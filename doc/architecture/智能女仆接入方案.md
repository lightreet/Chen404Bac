# 智能女仆接入方案

## 1. 背景与目标

本文档用于沉淀 `Chen404` 博客接入“智能女仆 + 文章知识问答”能力的项目计划与实施方案。

本文档的定位是：

- 面向后续开发实现的项目计划
- 明确当前已确认的产品决策与技术方向
- 作为前后端联动开发、接口设计、权限校验与验收的统一依据

本方案的核心目标：

- 在博客中接入一个具备“女仆角色感”的智能对话入口
- 让助手能够基于博客文章内容进行问答，而不是脱离站点内容的通用聊天
- 严格遵守博客现有文章可见性与登录权限规则，避免未授权内容泄露
- 尽量复用当前仓库已有的文章、页面、权限与 `Live2D` 组件基础，降低接入成本

需要明确的是：

- 这不是“给页面塞一个通用大模型聊天框”
- 也不是“让模型直接扫描整库后自由回答”
- 第一阶段目标是围绕文章内容构建一套可控、可追溯、可验收的 RAG 问答能力

---

## 2. 已确认决策

当前已确认的方案如下：

- 模型来源：云端 API
- 模型接入方式：OpenAI 兼容接口
- 知识范围：按登录权限过滤文章内容
- 前端入口：全站悬浮女仆入口
- 知识同步方式：文章发布/更新时增量同步，并提供手动全量重建入口

本阶段不再保留以下待定项：

- 不再讨论本地模型作为第一版默认方案
- 不再讨论“独立聊天页”作为主入口
- 不再采用“访问时临时全库检索”的低质量方案

---

## 3. 总体架构

总体采用“博客文章知识库 + 检索增强问答（RAG）+ 女仆前端入口”的架构。

```text
用户
  -> 全站悬浮女仆（前端 Live2D 升级）
  -> 聊天接口 POST /api/ai/chat
  -> 后端 AI 问答服务
      -> 文章权限过滤
      -> 文章知识片段检索
      -> Embedding 召回
      -> Chat Completion 生成回答
  -> 返回回答 + 引用文章 + 跳转链接
```

核心原则：

- 模型回答必须尽量基于博客文章内容生成
- 回答结果应附带引用来源，方便用户跳转核对
- 检索前必须先做权限过滤，而不是回答后再“补救”
- 找不到可靠依据时，应明确表示“未在当前博客文章中找到足够依据”

## 4. 后端改造方案

### 4.1 新增 AI 问答能力域

在 `Chen404Bac` 中新增独立 AI 能力域，建议拆分为以下职责：

- `AiChatController`
  - 提供对话接口
  - 接收前端消息、当前页面上下文、当前文章上下文
- `AiChatService`
  - 组织问答流程
  - 调用检索、权限过滤、模型生成
- `ArticleKnowledgeService`
  - 负责文章知识切分、清洗、入库、重建
- `EmbeddingService`
  - 调用 OpenAI 兼容 embedding 接口
- `ChatCompletionService`
  - 调用 OpenAI 兼容 chat completion 接口

建议把该能力作为独立业务域组织，避免散落在现有 `ArticleServiceImpl` 中直接堆叠复杂逻辑。

### 4.2 新增聊天接口

建议新增接口：

```text
POST /api/ai/chat
```

用途：

- 接收前端聊天消息
- 根据当前用户身份和页面上下文执行知识检索
- 返回回答与引用信息

建议请求字段：

- `messages`
- `currentArticleId`：当前若处于文章页则传入
- `pageContext`：可传当前页面类型，例如 `home` / `article` / `archive`
- `stream`：第一版可保留字段但不启用流式

建议响应字段：

- `answer`
- `citations`
- `relatedArticles`
- `traceId` 或等价请求标识，便于排障

### 4.3 新增知识同步流程

知识库同步需要挂接到现有文章生命周期中。

与当前代码链路的衔接建议：

- 在文章创建成功后：
  - 若文章为“已发布”状态，则生成知识片段并写入索引
- 在文章更新成功后：
  - 重建该文章对应的全部知识片段
- 在文章删除后：
  - 删除对应知识片段
- 在文章从“已发布”变为“非公开可索引状态”时：
  - 需要同步移出知识索引或标记不可检索

建议提供后台管理接口：

- `POST /api/admin/ai/reindex/articles`
  - 全量重建文章知识库
- 可选：`POST /api/admin/ai/reindex/articles/{id}`
  - 单篇重建

### 4.4 模型接入配置

建议通过 `application.yml` 扩展统一配置：

- `app.ai.enabled`
- `app.ai.base-url`
- `app.ai.api-key`
- `app.ai.chat-model`
- `app.ai.embedding-model`
- `app.ai.top-k`
- `app.ai.max-context-articles`
- `app.ai.connect-timeout-ms`
- `app.ai.read-timeout-ms`

这样可以保持供应商可替换性，后续无论接 OpenAI、DeepSeek、硅基流动或其他 OpenAI 兼容服务，都不需要重构业务层接口。

## 5. 前端改造方案

### 5.1 复用现有 Live2D 组件

当前前端已有 `Live2D.vue` 与 `DefaultLayout.vue` 结构，可直接作为智能女仆入口基础。

第一阶段建议：

- 保留“女仆形象 + 悬浮入口”的交互形式
- 将当前随机气泡逻辑升级为真实聊天面板
- 入口全站可见，但在移动端可以降级为收起式按钮或底部抽屉

### 5.2 聊天面板能力

前端需要新增：

- 消息列表
- 输入框
- 发送按钮
- 加载态
- 接口异常提示
- 引用文章展示区
- 跳转相关文章的交互

推荐交互表现：

- 女仆语气保持柔和、轻量角色感
- 但回答内容优先准确、可核对，避免角色设定压过信息质量
- 若当前页面是文章详情页，可优先提示“要不要一起看看这篇文章的内容”

### 5.3 页面上下文传递

前端在调用聊天接口时，建议补充页面上下文：

- 当前路由
- 当前页面类型
- 当前文章 ID（若位于文章详情页）

这样可以实现：

- 在文章页优先参考当前文章
- 在首页或归档页更偏向站点整体内容问答

### 5.4 聊天入口与面板设计

结合当前 `Live2D.vue` 已有的悬浮女仆、气泡与工具栏，推荐把聊天能力设计为“两层入口”：

- 第一层：女仆本体 + 轻气泡提示
- 第二层：点击“对话”按钮后展开正式聊天面板

这样做的原因是：

- 保留当前女仆作为站点看板娘的轻量存在感
- 不会一上来就用大聊天框打断页面阅读
- 能兼容“闲聊陪伴”与“站内知识问答”两种场景

推荐桌面端交互：

- 女仆默认保持悬浮
- 点击工具栏“对话”按钮后，在女仆左侧或上方展开聊天卡片
- 聊天卡片关闭后，保留最近一条简短气泡作为“余温反馈”
- 若当前在文章页，可在首次展开时显示快捷问题：
  - `帮我总结这篇`
  - `这篇适合谁看`
  - `推荐两篇相关的`

推荐移动端交互：

- 女仆入口缩为右下角按钮或更小的角色卡片
- 点击后使用底部抽屉或全屏弹层承载聊天面板
- 保留角色头部区域，但减少大面积装饰动画，优先保证输入与阅读空间

聊天面板推荐结构：

- 顶部区域：角色名 `Lyra`、在线状态、关闭按钮
- 中部区域：消息列表
- 底部区域：输入框、发送按钮、停止生成按钮
- 辅助区域：快捷提问、引用文章卡片、相关文章推荐

视觉上建议遵循当前女仆设定：

- 面板语气活泼、轻盈，但整体布局不要“花”
- 角色感主要体现在欢迎语、加载文案、按钮文案和小状态提示里
- 正式知识回答的正文区仍应清楚、克制、便于扫读

### 5.5 前端组件拆分建议

建议不要把聊天能力继续全部塞在当前 `Live2D.vue` 中，而是拆成“角色容器 + 聊天面板 + 聊天状态管理”三层：

- `Live2D.vue`
  - 负责女仆形象、拖拽、展开/收起、轻气泡提示
- `Live2DChatPanel.vue`
  - 负责聊天 UI 主体
- `Live2DMessageList.vue`
  - 负责消息列表与滚动定位
- `Live2DComposer.vue`
  - 负责输入框、发送、停止生成、快捷提问
- `useMaidChat.ts`
  - 负责请求、流式解析、消息状态、会话上下文

前端建议维护的核心状态：

- `panelVisible`
- `activeSessionId`
- `messages`
- `isStreaming`
- `streamingMessageId`
- `pendingText`
- `citations`
- `relatedArticles`
- `lastError`
- `pageContext`
- `currentArticleId`

消息渲染建议：

- 用户消息右侧展示
- 女仆消息左侧展示，并带角色头像或小标识
- 流式输出时逐字刷新当前女仆消息
- 引用文章不要塞进正文末尾，而是用独立引用卡片展示
- 若是闲聊型回复，不强制展示引用区

### 5.6 女仆气泡与聊天面板协同规则

当前 `Live2D.vue` 已有气泡区，后续不建议让气泡承担完整聊天内容，而应只承担“短反馈”职责。

推荐规则：

- 气泡只显示一句短回复或状态提示
- 正式多轮对话全部进入聊天面板
- 当面板关闭时，女仆可偶尔用气泡做轻提醒
- 当面板打开时，自动降低随机气泡频率，避免打扰用户输入

例如：

- 闲聊开场：气泡里显示“今天想轻松聊聊，还是让我帮你找文章呀？”
- 点击发送后：气泡里短暂显示“我来看看哦……”
- 回答完成后：气泡显示正文首句或一句短总结

这样可以同时保留：

- Live2D 角色感
- 真正可用的聊天体验
- 页面阅读时的轻量陪伴感

## 6. 数据与接口设计

### 6.1 文章知识索引

第一版建议新增独立知识索引表，例如：

```text
article_ai_chunk
```

建议字段至少包含：

- `id`
- `article_id`
- `chunk_index`
- `title`
- `summary`
- `content_chunk`
- `status`
- `visibility`
- `author_id`
- `publish_time`
- `embedding`
- `created_at`
- `updated_at`

其中：

- `embedding` 的实际存储格式可根据技术选型决定
- 第一版可以先以可落地为优先，不强依赖专业向量数据库

### 6.2 知识切分策略

建议切分规则：

- 标题单独参与索引
- 摘要单独参与索引
- 正文按长度切分为多个 chunk
- 必要时保留前后文重叠，减少语义断裂

切分目标：

- 保证检索粒度合理
- 避免单段过长导致召回不稳定或 token 浪费
- 为引用文章片段提供更准确依据

### 6.3 第一版存储策略

第一版建议：

- 优先使用 MySQL 扩展表承载知识片段
- 先完成“可用、可控、可维护”的最小闭环
- 如后续文章规模显著增长，再评估迁移到 `pgvector`、`Qdrant`、`Milvus` 等方案

这意味着第一版重点不在“极致检索性能”，而在：

- 权限正确
- 答案可追溯
- 数据同步稳定
- 维护成本可接受

### 6.4 会话与对话历史设计

如果女仆要同时承担“闲聊陪伴”和“站内引导”，后端需要把“知识索引”和“会话历史”分开设计，不建议混在同一套表结构里。

推荐新增以下会话表：

```text
ai_chat_session
```

建议字段：

- `id`
- `user_id`
- `visitor_id`
- `title`
- `source_page`
- `source_article_id`
- `status`
- `last_message_at`
- `created_at`
- `updated_at`

说明：

- `user_id`：登录用户会话归属
- `visitor_id`：游客会话标识，可来自前端本地生成并持久化的匿名 ID
- `title`：可选，用首轮问题或自动摘要生成
- `source_page`：首次发起会话的页面类型，如 `home`、`article`、`about`
- `source_article_id`：若从文章页发起，则记录文章 ID

推荐新增消息表：

```text
ai_chat_message
```

建议字段：

- `id`
- `session_id`
- `role`
- `scene`
- `content`
- `status`
- `trace_id`
- `model_name`
- `prompt_version`
- `citations_json`
- `related_articles_json`
- `token_usage_json`
- `created_at`
- `updated_at`

字段说明：

- `role`：`user` / `assistant` / 可选 `system`
- `scene`：`helper` / `companion`
- `status`：`pending` / `streaming` / `completed` / `failed`
- `citations_json`：最终引用结果快照
- `related_articles_json`：推荐文章快照
- `token_usage_json`：可选，便于后续成本统计

第一版的历史策略建议：

- 前端每次请求只上传最近 `6` 到 `12` 条消息作为对话上下文
- 后端持久化完整轮次结果，用于排障、体验分析和后续会话恢复
- 不把整段历史原样全部塞回模型，避免 token 膨胀
- 后续如会话变长，再增加“历史摘要”字段做上下文压缩

为了兼顾隐私与成本，建议第一版只持久化：

- 用户消息原文
- 女仆最终回复
- 引用与推荐结果
- trace 信息

不建议持久化：

- 流式 delta 碎片
- 中间 prompt 明文
- 每一步检索原始大段上下文

### 6.5 会话上下文与角色场景路由

当前后端已经有：

- `AiMaidPromptBuilder`
- `AiMaidPromptScene.HELPER`
- `AiMaidPromptScene.COMPANION`
- `AiMaidPromptContext`

因此正式聊天链路建议按以下流程组织：

```text
接收请求
  -> 识别会话 ID / 创建会话
  -> 识别场景 helper / companion
  -> 构建页面上下文 AiMaidPromptContext
  -> 若为 helper，执行权限过滤 + 内容检索
  -> 调用 AiMaidPromptBuilder 生成系统 prompt
  -> 调用 LLM
  -> 解析结果
  -> 落库消息与引用
  -> 返回给前端
```

推荐场景路由规则：

- 当前页面是文章页，且问题包含“这篇”“总结”“重点”“推荐”等内容时，优先进入 `helper`
- 用户问题明显是轻闲聊、打招呼、求安慰、求打气时，进入 `companion`
- 若用户闲聊中出现“给我找一篇”“这个站里有没有”这类内容，再自然切回 `helper`

这套设计可以保证：

- Lyra 始终是同一个角色
- 但后端对“知识回答”和“轻陪聊”有不同的运行边界

### 6.6 聊天接口与返回结构

建议把聊天接口拆成两类：

- `POST /api/ai/chat`
  - 非流式，适合 MVP 与接口联调
- `POST /api/ai/chat/stream`
  - 流式，适合正式聊天体验

非流式请求建议：

- `sessionId`
- `messages`
- `pageContext`
- `currentArticleId`
- `currentArticleTitle`
- `mode`
- `stream`

非流式响应建议：

```json
{
  "sessionId": "sess_xxx",
  "messageId": "msg_xxx",
  "scene": "helper",
  "replyText": "这篇主要在讲接入思路和权限边界，我可以再帮你压成三条重点。",
  "mood": "happy",
  "citations": [
    {
      "articleId": 101,
      "articleTitle": "智能女仆接入方案",
      "url": "/article/101",
      "snippet": "第一阶段目标是围绕文章内容构建一套可控、可追溯、可验收的 RAG 问答能力。"
    }
  ],
  "relatedArticles": [],
  "suggestions": [
    "帮我总结这篇",
    "推荐两篇相关文章"
  ],
  "traceId": "trace_xxx",
  "finishReason": "stop"
}
```

说明：

- `replyText`：专门给女仆说的话，必须短
- `citations`：给前端引用卡片区使用
- `relatedArticles`：给推荐阅读区使用
- `suggestions`：给快捷追问区使用

### 6.7 流式返回协议建议

第一版如果要上流式，建议优先采用 `text/event-stream`，并继续使用 Spring MVC 的 `SseEmitter`，不必为了聊天先整体切到 WebFlux。

原因：

- 现有项目更像传统 Spring MVC 结构
- 流式聊天只需要单接口流式返回，不值得整站改为响应式体系
- `SseEmitter` 足够支撑第一版女仆对话输出

建议流式事件：

- `session`
- `message_start`
- `delta`
- `citation`
- `related_article`
- `done`
- `error`

推荐事件示例：

```text
event: session
data: {"sessionId":"sess_xxx","messageId":"msg_xxx","scene":"helper"}

event: delta
data: {"messageId":"msg_xxx","text":"这篇主要在讲"}

event: delta
data: {"messageId":"msg_xxx","text":"接入思路和权限边界，"}

event: citation
data: {"articleId":101,"articleTitle":"智能女仆接入方案","url":"/article/101"}

event: done
data: {"messageId":"msg_xxx","finishReason":"stop","traceId":"trace_xxx"}
```

前端展示建议：

- 收到 `session` 时创建一条空的女仆消息
- 收到 `delta` 时把文本持续追加到当前消息
- 收到 `citation` 时逐步更新引用卡片区
- 收到 `done` 时把消息状态改为完成
- 收到 `error` 时结束流并显示“这次我没接稳，再试一次呀”

不建议把流式引用内容直接插入正文流里，否则前端很难稳定排版。

### 6.8 流式与非流式共存策略

推荐第一阶段采用“双通道同结构”策略：

- 开发联调阶段先用 `/api/ai/chat`
- 前端消息模型从一开始就按流式兼容来设计
- 正式上线时优先启用 `/api/ai/chat/stream`
- 非流式接口作为降级兜底

这样可以避免：

- 先写一套非流式前端，后面再重构一遍
- 流式失败时前端完全不可用
- 后端一开始就被流式细节拖慢整体落地

---

## 7. 权限与安全边界

这是本方案最关键的约束之一。

### 7.1 权限复用原则

AI 问答的可见性规则必须严格复用现有文章权限体系，包括但不限于：

- 公开可见
- 登录可见
- 好友可见
- 私密不可见

建议直接复用后端现有访问控制判断逻辑，避免重新发明一套平行权限系统。

### 7.2 禁止未授权内容泄露

必须避免以下风险：

- 游客通过提问得知登录可见文章内容
- 普通登录用户通过提问得知好友可见文章内容
- 私密文章标题、摘要、片段被引用到回答中
- 模型在“无依据”时胡乱补全文本，造成信息误导

因此要求：

- 先过滤可见文章，再做检索
- 返回引用时也必须再次确认文章权限
- 找不到依据时明确说“没有找到足够证据”

### 7.3 模型输出约束

建议对 system prompt 或服务端回答协议做明确约束：

- 优先根据博客文章内容回答
- 如果博客文章里没有明确提到，不要编造
- 如果证据不足，应直接说明无法确认
- 回答尽量附带引用文章标题和链接

## 9. 验收标准

以下场景通过后，才视为第一版达到可交付状态。

### 9.1 内容可用性

- 助手能够基于博客公开文章回答常见问题
- 当前位于文章详情页时，能优先参考当前文章内容
- 回答中能够展示相关引用文章

### 9.2 权限正确性

- 游客只能问到公开文章
- 登录用户只能问到自己有权限查看的文章
- 未授权文章不会通过 AI 回答暴露标题、摘要或正文片段

### 9.3 数据同步正确性

- 新发布文章可以进入知识库并被检索
- 更新文章后，回答结果能够反映最新内容
- 删除文章后，引用不会继续残留

### 9.4 失败兜底能力

- 未命中知识库时，明确返回“暂无足够依据”
- 模型调用失败时，前端有清晰提示
- 后端记录可排查日志，不出现静默失败

### 9.5 对话体验可用性

- 女仆回复长度符合“日常对话”预期，不长篇大论
- 面板打开、关闭、发送、流式生成流程稳定
- 流式输出过程中，用户可以看到逐步生成的内容
- 关闭面板后，再次打开能够恢复当前会话
- 闲聊回复与知识回复都保持统一角色感，不会一会儿像客服一会儿像通用 AI

## 10. 后续可演进项

第一版完成后，可根据实际效果逐步扩展：

- 流式输出，提升对话体验
- 会话记忆与上下文压缩

- 向量数据库升级，提升规模化检索能力

需要强调：

- 第一版优先保证权限正确、问答可追溯、接入稳定

## 11. 本阶段结论

本项目的智能女仆接入，第一阶段应聚焦于：

- 复用现有前端 `Live2D` 能力作为全站悬浮入口
- 基于博客文章建立可控的知识检索问答链路
- 使用 OpenAI 兼容云端接口接入模型
- 复用现有文章权限逻辑，防止未授权内容泄露
- 通过增量同步与后台重建机制保证知识库内容更新

该方案适合作为当前仓库后续实现的正式项目计划基础。
