# 旅行纪念地图功能方案

> 更新时间：2026-05-22

## 1. 当前结论

旅行纪念地图已经从“待新增功能”进入“基础功能已落地，地图展示内核待升级”的阶段。

当前项目已经具备：

- 前台 `/memory-map` 独立页面
- 前台地点列表、地图选点、右侧旅行详情、照片墙预览
- 前台详情页 `/memory-map/detail/:id`
- 管理员创建页 `/memory-map/create`
- 管理员编辑页 `/memory-map/edit/:id`
- 后端地点主表与照片子表
- 后端前台查询接口、后台管理接口、图片上传与 EXIF 解析
- 管理员与知友可见、仅管理员可维护的权限模型
- 站点后台对旅行地图封面图与封面位置的配置能力

下一阶段的核心工作不是继续接入高德地图做主展示，而是把前台展示地图升级为：

1. 第一优先：市级 GeoJSON + 自定义 SVG 渲染
2. 第二优先：市级 GeoJSON + ECharts `geo/map`
3. 不推荐：继续使用高德地图作为前台主展示地图

高德地图仍可保留在后台手动选点场景，因为后台更需要坐标准确与搜索选点；前台主展示更需要审美统一、无第三方地图 Logo、可控的视觉层级和纪念感。

近期改造需要先明确三条边界：

- 第一阶段只优化当前展示地图的缩放、拖拽和平移体验，不动后端接口和数据表。
- 市级 GeoJSON 改造开始前，必须先确定坐标系统一策略和地图数据许可证。
- 前台正式环境不应在接口失败时展示演示数据，演示数据只能作为开发预览或设计验收材料。

---

## 2. 功能定位

旅行纪念地图不是 GIS 工具，也不是普通相册页。

它在项目中的定位是：

- 用地图承载旅行记忆
- 用地点聚合照片、备注和感想
- 面向管理员与知友的小范围展示
- 作为博客内容之外的生活记录专题页

页面体验应围绕三件事展开：

- 地图负责“我去过哪里”
- 右侧详情负责“这个地点发生了什么”
- 照片墙负责“按视觉和情绪慢慢浏览”

因此地图展示的视觉目标不是地图服务的产品感，而是“私人旅行手账中的一张可交互地图”。

### 3.2 前台首页结构

`MemoryMap.vue` 当前结构为：

- 顶部封面使用统一 `PageHero`
- 无权限用户展示 `FeatureAccessCover`
- 有权限用户进入旅行地图主体
- 主体采用左右页结构：
  - 左侧：`旅行足迹` + `TravelMemoryMap`
  - 右侧：当前地点旅行详情或空状态
- 下方：照片墙预览
- 管理员可看到“新增旅游地点”入口

当前页面的真实数据策略为：

- 正常情况读取 `getTravelMemories()`
- 如果接口返回空列表，展示空状态，引导管理员新增地点
- 如果请求失败，展示错误提示，不使用演示数据伪装成真实数据

`demoTravelMemories.ts` 当前仅适合作为开发期预览素材或设计验收材料，不建议在正式运行链路中自动兜底。否则接口异常时页面仍显示“正常旅行数据”，会掩盖线上故障，也会影响真实验收。

### 3.3 前台封面配置

旅行地图封面当前复用站点统一封面能力。

后台配置入口位于站点设置：

- `memory-map` 封面图
- `memory-map` 封面位置

前端通过 `resolveFeatureHero(siteConfig, 'memory-map')` 读取配置。

这意味着：

- 封面图支持后台自定义
- 封面位置支持后台自定义
- 页面主体样式调整不应破坏封面配置链路

### 3.4 地图组件当前实现

`TravelMemoryMap.vue` 当前有两套模式：

| 模式 | 使用场景 | 当前实现 |
| --- | --- | --- |
| 展示模式 | 前台旅行地图首页 | `@svg-maps/china` + 自定义 SVG 标记点与路线 |
| 选点模式 | 管理员创建/编辑地点 | 高德地图 JS API |

展示模式当前能力：

- 使用 `@svg-maps/china` 渲染中国地图
- 根据地点经纬度投影到 SVG 坐标
- 支持地点标记点
- 支持当前地点高亮
- 支持路线曲线
- 支持放大、缩小、重置

展示模式当前限制：

- `@svg-maps/china` 是省级地图，不包含市级边界
- 当前缩放上限为 `1.18`，放大后细节有限
- 当前展示模式没有鼠标左键拖拽平移
- 城市点位来自经纬度粗投影，不等同于真实市级区域边界
- 地图视觉可以做成纪念感，但无法真正精确到市级行政区轮廓

选点模式当前能力：

- 通过 `loadAmap()` 加载高德地图
- 支持管理员在地图上选择经纬度
- 适合后台录入和坐标校准

选点模式保留理由：

- 后台选点重视准确性和操作效率
- 高德有成熟的拖拽、缩放、定位和地图交互
- 后台出现地图 Logo 对前台审美影响较小

## 4. 设计目标与页面原则

### 4.1 页面设计目标

页面本质是“用地图承载旅行记忆”，不是“展示一张地图”。

核心目标：

1. 用户能快速看到去过哪些地方
2. 用户能点击地点查看照片、时间和感想
3. 用户能通过照片墙沉浸浏览所有旅行
4. 管理员能方便新增和维护地点

### 4.2 布局原则

当前主体布局应保持：

- 左侧地图作为主视图
- 右侧详情作为信息面板
- 底部照片墙作为情绪浏览区

职责划分：

| 区域 | 职责 |
| --- | --- |
| 地图 | 选择地点、展示路线、表达去过哪里 |
| 右侧详情 | 展示当前地点照片、时间、备注、感想 |
| 照片墙 | 横向浏览全部旅行记忆 |

### 4.3 视觉原则

当前页面已逐步向“背景淡 + 卡片白 + 重点粉”收敛。

后续继续遵循：

- 粉色用于按钮、选中态、路线和少量强调
- 普通文字不使用大面积粉色
- 地图本身保持低对比，不喧宾夺主
- 标题字体统一，避免手写字体、衬线字体、英文字体混用过多
- 页面内部标题保持克制，不使用封面级字号

## 5. 为什么不继续用高德做前台主地图

前台主展示不建议继续使用高德地图，主要原因如下：

| 问题 | 影响 |
| --- | --- |
| 地图 Logo 与服务控件不可完全融入设计 | 破坏私人纪念地图的整体气质 |
| 默认地图样式偏产品地图 | 与当前樱花、手账、纸质卡片氛围不统一 |
| 视觉细节不可完全控制 | 难以实现类似定制插画地图的效果 |
| 前台主要需求不是导航和搜索 | 高德能力过重，审美控制不足 |

高德仍适合保留在后台选点：

- 管理员可以精准选择经纬度
- 可以后续扩展地点搜索
- 操作效率高
- 后台不是最终展示体验，不需要追求完全无 Logo 的纪念感

## 6. GeoJSON 与 SVG 地图升级方案

### 6.1 GeoJSON 是什么

GeoJSON 是一种用 JSON 表达地理数据的格式。

对本项目最有用的是 `FeatureCollection`：

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": {
        "name": "厦门市",
        "adcode": "350200",
        "province": "福建省"
      },
      "geometry": {
        "type": "Polygon",
        "coordinates": []
      }
    }
  ]
}
```

其中：

- `properties` 保存城市名、行政区划码、省份等业务可读信息
- `geometry` 保存城市边界坐标
- 前端可以把 `geometry` 投影成 SVG `path`

### 6.2 GeoJSON 能做到什么

引入市级 GeoJSON 后，前台地图可以做到：

- 绘制真实市级边界
- 当前城市区域高亮
- 鼠标 hover 城市区域
- 点击城市区域切换右侧详情
- 经纬度点位落在更准确的地图区域上
- 城市名 label 基于区域中心或自定义 label 坐标显示
- 放大后仍能看到市级轮廓，而不是只有省级轮廓

需要明确的是：

- GeoJSON 可以定位到市级区域
- 经纬度可以定位到市内具体点
- 视觉上是否显示完整市级细节，取决于 GeoJSON 精度、简化程度和当前缩放比例

### 6.3 第一优先方案：市级 GeoJSON + 自定义 SVG 渲染

这是最符合当前页面气质的方案。

实现方式：

1. 前端准备市级 GeoJSON 数据
2. 使用 `d3-geo` 将经纬度投影到 SVG 坐标
3. 将城市边界渲染为 SVG `path`
4. 使用当前已有地点经纬度绘制旅行标记点
5. 使用 SVG 路径绘制旅行路线
6. 使用前端状态控制缩放、拖拽、选中态和动画

当前项目已经有 `d3-geo` 依赖，因此可以继续沿用，不必为了第一版引入额外地图渲染库。

推荐新增文件结构：

```text
Chen404Fro/src/assets/maps/
  china-city-boundaries.geo.json
  china-city-labels.json
  china-map-manifest.ts

Chen404Fro/src/components/TravelMemoryMap/
  TravelMemoryMap.vue
  mapProjection.ts
  mapTypes.ts
```

职责划分：

| 文件 | 职责 |
| --- | --- |
| `china-city-boundaries.geo.json` | 市级边界数据 |
| `china-city-labels.json` | 城市 label 微调坐标，可覆盖自动质心 |
| `china-map-manifest.ts` | 地图数据版本、简化级别、数据来源说明 |
| `mapProjection.ts` | `d3-geo` 投影、坐标转换、路径生成 |
| `mapTypes.ts` | GeoJSON properties 与地图渲染状态类型 |
| `TravelMemoryMap.vue` | 负责交互状态与 SVG 渲染 |

### 6.4 坐标系统一策略

市级 GeoJSON 改造前，必须先统一坐标系，否则 marker、路线和城市边界会出现肉眼可见的偏移。

当前系统存在两类坐标来源：

- EXIF 解析得到的照片坐标，通常可按 WGS84 理解
- 高德地图选点得到的坐标，属于 GCJ-02

近期建议采用以下规则：

- 数据库中的 `travel_memory_location.latitude` / `longitude` 作为“前台展示坐标”，目标统一为 WGS84。
- 后台高德选点后，前端提交前将 GCJ-02 转为 WGS84；如仍需高德逆地理编码，则调用高德前再临时转回 GCJ-02。
- EXIF 坐标直接按 WGS84 回填；如果后续发现机型或来源异常，再在上传解析层补来源标记。
- 已有历史坐标暂不做盲目批量转换，因为当前表里没有 `coordinate_system` 字段，无法可靠判断每条数据来自 EXIF 还是高德。
- 历史数据通过管理员编辑保存逐步归一；必要时后续再增加 `coordinate_system` 或 `city_code` 辅助回填。

第一阶段交互优化不依赖坐标系改造，可以先做；市级 GeoJSON 渲染开始前必须完成坐标转换工具和新数据保存规则。

### 6.5 自定义 SVG 能实现的成品层次

第一版可实现到以下效果：

- 左侧地图卡片内是一张浅色纸质中国地图
- 市级边界以极浅描边显示
- 旅行地点用樱花印章样式标记
- 当前选中地点有柔和光圈与轻微放大
- 已去城市之间用粉色虚线路线串联
- 右下角展示简洁提示或图例
- 鼠标滚轮缩放
- 鼠标左键拖拽平移
- 点击地点点位切换右侧详情
- 点击照片墙卡片同步选中地图点

自定义 SVG 的优势：

- 无第三方 Logo
- UI 层级完全可控
- 与现有樱花、纸张、手账风格一致
- 可保留当前已有的标记点、路线、照片墙联动逻辑
- 未来可扩展城市区域 hover 与高亮

### 6.6 第二优先方案：市级 GeoJSON + ECharts

ECharts 方案适合作为备选。

优点：

- 内置地图缩放、拖拽、tooltip、select
- GeoJSON 注册后即可渲染地图
- 交互开发速度较快
- 大数据量地图下性能和事件模型更成熟

缺点：

- 当前项目尚未引入 ECharts
- 视觉深度定制不如自定义 SVG 自由
- 手账感、纸质感、印章感需要绕过 ECharts 默认图表风格
- 最终效果容易偏“数据看板地图”

建议只有在自定义 SVG 性能或交互成本明显超预期时，再切换到 ECharts。

### 6.7 不建议方案：继续高德展示主地图

不建议继续高德作为前台主地图。

但后台手动选点继续使用高德是合理的。

最终推荐状态：

| 场景 | 地图方案 |
| --- | --- |
| 前台展示 | GeoJSON + 自定义 SVG |
| 后台选点 | 高德地图 |
| 后续复杂地图分析 | 再评估 ECharts |

## 7. 地图升级实施计划

### 7.1 第 0 阶段：保留现状并明确边界

当前已经完成：

- 基础前台展示
- 后台录入流程
- 接口与数据表
- EXIF 解析
- 图片文件引用维护
- 开发期演示数据素材

这一阶段不再继续扩大旧展示地图能力，避免在省级 SVG 上投入过多不可复用成本。

### 7.2 第 1 阶段：先优化当前 SVG 交互

在引入市级 GeoJSON 前，可以先把当前展示模式的交互补齐。

改动范围：

- `TravelMemoryMap.vue`

建议实现：

- 增加鼠标左键拖拽平移
- 增加滚轮缩放
- 将最大缩放从当前 `1.18` 提升到约 `2.6` 到 `3`
- 缩放重置时同时重置平移
- 点击 marker 时避免误触发拖拽
- 地图容器加 `cursor: grab` / `cursor: grabbing`
- 图例文案改为“滚轮缩放，按住左键拖动地图”

这一阶段能解决用户当前直接感知到的问题：

- 放大程度有限
- 放大后不能拖动查看
- 地图像固定图片，不像可浏览地图

但这一阶段不会解决“市级边界精细度不足”，因为数据源仍是省级 SVG。

实现约束：

- 仅改 `TravelMemoryMap.vue` 展示模式，不影响 `pickerMode` 下的高德地图选点。
- 平移状态和缩放状态集中管理，避免按钮缩放、滚轮缩放和拖拽各自维护状态。
- 鼠标拖拽需要设置移动阈值，区分点击 marker 和拖动地图。
- 移动端第一版只保证基础查看、点击 marker、按钮缩放和重置；复杂双指缩放可放到市级地图阶段再评估。

### 7.3 第 2 阶段：引入市级 GeoJSON 数据

新增地图数据前，需要先确认数据来源与许可证。

数据要求：

- 至少包含中国地级市边界
- 每个 `Feature` 应包含 `name` 和 `adcode`
- 推荐包含 `province` 或可通过 `adcode` 映射省份
- 坐标系统需要明确，优先使用 WGS84
- 文件大小需要可控，避免首屏加载过慢

推荐处理方式：

- 将原始 GeoJSON 放到离线处理脚本输入目录
- 使用脚本做简化、字段清洗、排序和大小检查
- 前端只提交处理后的轻量文件
- 处理后的 GeoJSON 建议放到前端 `public/maps/` 下，通过 `fetch` 在 `/memory-map` 页面按需加载
- 不建议在 `TravelMemoryMap.vue` 中静态 `import` 大体积 GeoJSON，避免进入首屏主包
- 文件名带版本或内容摘要，例如 `china-city-boundaries.v1.geo.json`，便于浏览器缓存和后续替换
- `china-map-manifest.ts` 只保存数据版本、来源、许可证、文件路径和简化级别，不承载大体积边界数据本身

可接受的数据形态：

```ts
interface ChinaCityFeatureProperties {
  name: string
  adcode: string
  province?: string
  center?: [number, number]
}
```

如果 GeoJSON 体积过大，可拆分为：

- 全国低精度文件：默认展示
- 省份或区域高精度文件：放大或选中后懒加载

第一版建议先使用全国中低精度市级文件，保证实现闭环。

进入这一阶段前需要完成：

- 坐标转换工具已经落地，并明确 WGS84 / GCJ-02 的输入输出边界。
- 地图数据来源与许可证已经记录到 manifest。
- 地图数据体积经过构建或脚本检查，避免明显拖慢 `/memory-map` 首次加载。

### 7.4 第 3 阶段：重构 `TravelMemoryMap` 展示模式

展示模式重构目标：

- 保留 `pickerMode` 下的高德选点能力
- 将非 `pickerMode` 从 `@svg-maps/china` 切换为市级 GeoJSON 渲染
- 保留现有 `locations`、`activeId`、`select` 组件接口
- 尽量不影响上层 `MemoryMap.vue`

建议组件输入保持：

```ts
locations: TravelMemoryLocationListItem[]
activeId?: number | null
pickerMode?: boolean
modelValue?: { latitude?: number; longitude?: number }
```

建议组件事件保持：

```ts
select(locationId: number)
update:modelValue({ latitude, longitude })
```

新增内部状态：

```ts
scale: number
pan: { x: number; y: number }
isDragging: boolean
hoveredAdcode: string | null
selectedAdcode: string | null
```

核心渲染层：

1. 背景纸张层
2. 城市边界层
3. 已去城市高亮层
4. 路线层
5. 地点标记层
6. 城市 label 层
7. 控制按钮层

### 7.5 第 4 阶段：城市匹配与区域高亮

当前后端地点已有：

- `province`
- `city`
- `latitude`
- `longitude`

第一版城市匹配可使用：

1. 优先经纬度投影展示 marker
2. 使用 `city` 名称匹配 GeoJSON `properties.name`
3. 匹配成功则高亮城市区域
4. 匹配失败仍展示 marker，不阻断页面

第一版验收口径应明确为：marker 必须正确展示，城市区域高亮属于尽力匹配。不要把“所有城市都能稳定高亮”作为无行政区划码阶段的硬性验收目标。

为了提高名称匹配成功率，前端可以增加轻量归一化工具：

- 去掉 `市`、`地区`、`盟`、`自治州`、`特别行政区` 等常见后缀
- 兼容 `厦门` / `厦门市` 这类短名
- 为少量真实数据中的特殊城市维护 `city-aliases.ts`
- 匹配失败时记录开发日志或调试标记，方便后续决定是否补 `city_code`

后续如果需要更稳定的市级匹配，建议新增字段：

- `province_code`
- `city_code`

对应前端类型可扩展：

```ts
interface TravelMemoryLocationListItem {
  provinceCode?: string
  cityCode?: string
}
```

是否新增数据库字段可以放到市级 GeoJSON 引入之后再决定。

原因：

- 当前经纬度已经足够绘制 marker
- 市名匹配可先满足大多数展示需求
- 过早加行政区划码字段会增加录入成本

如果近期目标从“地图点位展示”升级为“城市区域必须稳定高亮”，则应提前新增 `province_code` / `city_code`。否则第一版应保持轻量匹配，不扩大后端改造范围。

### 7.6 第 5 阶段：照片墙与地图联动增强

地图内核升级后，照片墙可以增强联动：

- 点击照片墙城市卡片时地图平滑移动到该地点
- 选中地图点时照片墙自动滚动到对应卡片
- 当前城市在地图、右侧详情、照片墙三处保持同一选中态

这一阶段不需要改后端，主要是前端状态联动。

## 8. 后端是否需要改动

### 8.1 近期不需要改动接口

市级 GeoJSON + SVG 展示的第一版，不需要新增后端接口。

原因：

- 地图边界是静态前端资源
- 地点经纬度已经在现有接口返回
- 地点标题、省份、城市已经足够做初版匹配
- 管理员选点仍使用现有创建/编辑流程

但近期需要补一条前后端约定：地点展示坐标以 WGS84 作为目标标准。这个约定不一定要求立即改接口字段，但会影响后台选点提交、EXIF 回填和前台投影。

### 8.2 后续可能新增字段

如果后续要让城市区域高亮更稳定，可以新增：

- `province_code`
- `city_code`

使用场景：

- 避免“厦门”与“厦门市”名称不一致导致匹配失败
- 支持同名地区或特殊行政区划
- 与 GeoJSON `adcode` 直接关联

建议新增时同步更新：

- 数据库迁移
- `TravelMemoryLocation`
- `CreateTravelMemoryCommand`
- `UpdateTravelMemoryCommand`
- `TravelMemoryLocationListItemVO`
- `TravelMemoryLocationDetailVO`
- 前端 `TravelMemoryLocationListItem`
- 前端创建/编辑表单

新增字段的推荐触发条件：

- 市级 GeoJSON 已接入，但真实数据中城市名称匹配失败较多
- 需要点击城市区域而不是 marker 来稳定定位地点
- 后续要支持按城市、地区做筛选或聚合统计
- 管理端已经可以从高德逆地理编码中拿到可靠 `adcode`

如果只是近期优化地图浏览体验和 marker 展示，可以暂缓新增字段。

### 8.3 后台选点可继续沿用高德

后台选点不建议短期重写。

理由：

- 当前高德选点已经满足管理员录入坐标
- 自定义 SVG 地图更适合展示，不适合精确找点
- 后台选点可以接受地图服务的产品化控件

## 10. 验收标准

### 10.1 已落地功能验收

当前基础功能应满足：

- 游客和普通用户无法查看旅行地图内容
- 知友可以查看旅行地图
- 管理员可以查看、创建、编辑、删除旅行地点
- 前台可以展示地点列表
- 点击地图地点可以切换右侧详情
- 详情页可以展示地点完整内容
- 上传旅行图片可以返回图片地址
- 有 EXIF 的图片可以返回经纬度和拍摄时间
- 无 EXIF 的图片上传不失败，可手动选点
- 没有真实数据时，前台展示空状态，不自动混入演示数据
- 接口请求失败时，前台展示错误提示，不自动混入演示数据
- 旅行地图封面可通过后台站点设置配置

### 10.2 地图交互升级验收

第 1 阶段交互升级完成后，应满足：

- 鼠标滚轮可以缩放地图
- 鼠标左键按住可以拖动地图
- 放大到 `2.6` 到 `3` 倍时仍能平移查看
- 点击地点不会被拖拽误判
- 重置按钮可以恢复初始缩放和平移
- 桌面端布局不破坏
- 移动端至少支持点击 marker、按钮缩放和重置，复杂手势不作为第一阶段硬性目标

### 10.3 市级 GeoJSON 升级验收

市级地图升级完成后，应满足：

- 前台主地图不再依赖高德展示
- 前台地图无第三方地图 Logo
- 地图可以绘制市级边界
- 已有地点可以正确投影到地图区域
- 当前选中地点有明确高亮
- 至少能通过城市名归一化匹配高亮部分真实城市；未匹配城市仍展示 marker
- 匹配失败时页面不报错，仍展示地点 marker
- 地图支持缩放、拖拽、重置
- 地图风格与当前旅行地图页面一致

## 11. 风险与处理

### 11.1 GeoJSON 数据许可证风险

风险：

- 地图边界数据可能存在许可证限制
- 不能随意把未知来源数据提交进仓库

处理：

- 引入前确认数据来源和许可证
- 在 `china-map-manifest.ts` 记录数据来源、处理方式和版本
- 必要时只提交处理后的简化数据，并保留来源说明

### 11.2 GeoJSON 文件体积风险

风险：

- 全国市级边界文件可能影响首屏加载

处理：

- 先使用中低精度简化版本
- 控制字段，只保留渲染和匹配需要的属性
- 后续再考虑按区域拆分懒加载

### 11.3 城市匹配风险

风险：

- 后台录入的 `city` 与 GeoJSON `name` 不一致
- 例如“厦门”和“厦门市”

处理：

- 前端做基础归一化，去掉“市”“地区”“自治州”等后缀进行辅助匹配
- 匹配失败时仍显示 marker
- 后续通过 `city_code` 与 `adcode` 建立稳定关系

### 11.4 投影与坐标偏差

风险：

- 不同地图数据坐标系不同
- 经纬度投影后可能与边界有偏移
- 当前历史数据没有坐标系字段，无法可靠判断每个坐标是否来自 EXIF 或高德选点

处理：

- 优先选用 WGS84 GeoJSON
- 使用同一投影函数同时处理边界、marker、路线和 label
- 新增数据以 WGS84 作为前台展示标准
- 高德选点坐标提交前转换为 WGS84；调用高德逆地理编码前按需转回 GCJ-02
- 历史数据不做无依据的批量转换，优先通过管理员编辑保存逐步归一
- 如后续需要自动回填历史数据，应先增加 `coordinate_system` 或借助可信来源判断

### 11.5 交互复杂度风险

风险：

- SVG 拖拽、缩放、点击、hover 同时存在，容易出现误触

处理：

- 拖拽设置移动阈值
- marker 点击阻止事件冒泡
- 缩放和平移状态集中管理
- 移动端先保证基础查看，不追求复杂手势

## 12. 推荐开发顺序

建议按以下顺序推进：

1. 保持现有后端接口和管理流程不变
2. 先在 `TravelMemoryMap.vue` 补齐拖拽、滚轮缩放和更合理缩放上限
3. 明确 WGS84 / GCJ-02 坐标转换边界，并补前端转换工具

5. 新增地图数据文件、manifest 与投影工具

8. 加入城市区域高亮和城市名归一化匹配
9. 优化照片墙、右侧详情和地图的联动
10. 根据实际匹配效果决定是否新增 `city_code` / `province_code`

## 14. 当前技术决策

当前项目的地图技术决策为：

- 前台主展示：从省级 `@svg-maps/china` 逐步升级到市级 GeoJSON + 自定义 SVG
- 后台选点：继续保留高德地图
- 数据接口：近期不新增地图接口，继续使用现有地点接口
- 数据模型：近期不强制新增行政区划码，先通过城市名和经纬度完成 marker 展示，城市区域高亮采用尽力匹配
- 坐标标准：前台展示目标统一为 WGS84，市级 GeoJSON 改造前补齐高德 GCJ-02 与 WGS84 的转换边界
- 视觉方向：地图服务产品感让位于私人旅行纪念感

这条路线能最大程度复用当前已实现的后端、管理端和前台页面，同时解决当前最明显的问题：

- 前台地图不够精细
- 放大后缺少可浏览能力
- 高德地图样式和 Logo 不适合作为最终主展示
- 页面需要与当前旅行手账风格保持统一
