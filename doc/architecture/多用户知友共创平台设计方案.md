# Chen404 多用户知友共创平台设计方案

> 文档状态：方案设计
>
> 适用范围：`Chen404Bac`、`Chen404Fro`，以及与文件存储相关的部署配置
>
> 首次编写：2026-07-27
>
> 目标版本：分阶段实施，不要求一次性完成全部模块

## 1. 背景与结论

Chen404 当前产品形态是“公开阅读 + 知友私密访问 + 站长内容维护”。账号注册、登录、知友申请、文章作者字段、旅行地点创建人字段、上传文件所有者字段、公开成员主页等基础能力已经存在，但文章、旅行和音乐的写入口仍主要由管理员独占。

本次演进不应把 Chen404 改造成开放注册、开放投稿的泛社区，而应定位为：

> 一个由站长维护、知友参与创作、公开读者自由浏览的邀请制共创空间。

目标形态包含三类表面：

1. 公开阅读世界：文章、旅行地图、音乐馆、留言板和成员主页。
2. 知友创作工作台：管理自己的文章、旅行地点和音乐。
3. 管理员治理后台：维护全站分类、推荐内容、公共歌单、知友资格、消息中心、站点配置和违规内容。

本次改造的核心不是重新建设认证系统，而是补齐以下四条边界：

- 创作资格：谁可以创建哪类内容。
- 资源所有权：谁可以修改和删除某一条内容。
- 发布流程：内容处于草稿、已发布还是归档状态。
- 访问范围：游客、登录用户、知友和管理员分别能看到什么。

## 2. 现状基线

### 2.1 已有基础

当前系统已经具备：

- `sys_user.trust_level`：区分读者与知友。
- `sys_role` / `sys_user_role`：区分普通用户与管理员。
- 好友申请提交、后台审批和邮件审批流程。
- `article.author_id`：文章天然具备作者归属。
- `travel_memory_location.created_by` / `updated_by`：旅行地点已经预留创建人与更新人。
- `sys_file.user_id`：上传文件已经记录上传者。
- `/articles/mine`：当前用户文章列表。
- `/articles?authorId=`：按作者查询公开文章。
- `/site/users/{id}`：公开成员资料。
- `/user/:id`：成员主页，并已展示该成员的公开文章。
- 文章公开、登录、知友、私密四种可见性。
- 旅行地点公开、知友两种可见性。
- 管理员全局维护文章、旅行地点和音乐的现有界面。

### 2.2 当前阻塞点

#### 文章

- `ArticleServiceImpl` 在创建、更新、删除时硬编码为仅管理员。
- `AccessServiceImpl.canManageArticle` 只允许管理员，没有使用已经存在的作者判断。
- 前端文章编辑路由要求管理员。
- 置顶、推荐等管理员能力与普通内容编辑能力尚未真正分开。

#### 旅行地图

- 地点虽有 `created_by`，但全部写接口位于 `/admin/travel-memories/**`。
- 服务层 `canManageTravelMemory` 只判断管理员。
- 前端创建与编辑路由同时带有 `requiresFriend` 和 `requiresAdmin`，实际仍只有管理员能进入。
- 列表没有按创建者筛选，也没有返回创建者公开资料。

#### 音乐馆

- `music_track` 没有创建者或所有者字段。
- 音频与封面上传接口只允许管理员。
- 曲目 CRUD、状态切换和歌单管理全部只允许管理员。

#### 管理员消息

- 当前没有统一的管理员消息表。
- 知友直接发布内容后，管理员缺少低打扰的新增内容汇总入口。
- 顶部导航头像没有未读消息数。
- 文章、旅行和音乐服务尚未发布可供消息中心消费的业务事件。

#### 文件与隐私

- MinIO 初始化策略会把现有桶设置为公共可读。
- “知友可见”目前只限制业务 API；如果图片 URL 已知，底层文件仍可能被直接访问。
- `convertToPermanent` 主要按 URL 转换文件状态，缺少统一的“该文件是否属于当前操作者、类型是否匹配”校验。
- 多用户开放上传后，必须增加单用户配额、频率限制和业务归属校验。

#### 公开用户资料

- 站点成员接口当前会返回邮箱。
- 成员列表目前会包含所有启用用户，读者注册规模扩大后不适合作为公开成员名录。
- 站长读取仍依赖固定用户 ID，应改成明确的站点所有者配置。

## 3. 设计目标与非目标

### 3.1 设计目标

1. 知友可以创建、编辑和删除自己的文章与旅行地点。
2. 知友可以创建、发布和管理自己的音乐。
3. 管理员可以管理所有用户内容，保留全站策展与治理权。
4. 旅行地图支持查看全部可见地点、我的地点和指定知友的地点。
5. 公开成员主页可以展示该成员的文章、旅行和音乐贡献。
6. 所有权限由后端最终裁决，前端只负责隐藏入口和改善交互。
7. 知友资格变化能够在下一次请求立即生效，不依赖旧 JWT 中的长期缓存权限。
8. 知友可见和草稿文件不能通过永久公开直链绕过业务鉴权。
9. 管理员可以从头像未读数和后台消息中心了解上线后的新增内容。
10. 保持现有公开页面的个人气质，不把产品改造成通用社区或企业后台。

### 3.2 非目标

首期不包含：

- 公开用户自由投稿。
- 关注、粉丝、私信、群聊。
- 实时协同编辑。
- 内容收益、打赏和结算。
- 知友自建全站分类。
- 知友维护公共歌单或默认电台。
- 完整的多级组织、租户或企业 RBAC。
- 复杂的推荐算法和用户画像。
- 站内举报中心、申诉中心等大型社区治理体系。

这些能力如果未来确有需要，应在真实使用数据出现后单独设计，避免首期过度平台化。

## 4. 产品角色与权限模型

### 4.1 用户角色

#### 游客

- 查看公开文章、公开旅行地点、已发布音乐和公开成员主页。
- 按站点配置参与游客评论。
- 不具备创作能力。

#### 注册读者

- 拥有游客能力。
- 管理个人资料。
- 点赞、收藏、评论。
- 提交知友申请。
- 不具备内容创作能力。

#### 知友

- 拥有注册读者能力。
- 查看知友可见内容。
- 创建、编辑和删除自己的文章。
- 创建、编辑和删除自己的旅行地点。
- 创建、发布和管理自己的音乐。
- 不能管理其他知友内容。
- 不能修改站点配置、全站分类、公共歌单和推荐位。

#### 管理员

- 拥有全部知友能力。
- 管理任意用户内容。
- 管理文章置顶、推荐和全站分类。
- 维护公共歌单并下架不适合继续公开的音乐。
- 审批知友申请、禁用用户、管理站点配置。
- 查看管理员消息、审计记录和文件治理信息。

### 4.2 四个正交维度

权限判断必须拆成四个维度，禁止继续用单一“是否管理员”覆盖所有问题。

| 维度 | 典型字段或来源 | 回答的问题 |
| --- | --- | --- |
| 身份与资格 | `roleCode`、`trustLevel`、能力集合 | 用户是否具备创建某类内容的资格 |
| 所有权 | `author_id`、`created_by`、`contributor_id` | 用户是否拥有当前资源 |
| 内容状态 | 草稿、已发布、归档 | 内容处于哪个生命周期阶段 |
| 可见性 | 公开、登录、知友、私密 | 当前访问者是否可以查看内容 |

所有权不等于可见性。例如作者可以查看自己的私密草稿，但其他知友不能查看。

身份不等于所有权。例如知友可以创建文章，但不能编辑另一位知友的文章。

管理员是全局治理例外，但管理员操作仍应留下审计记录。

### 4.3 默认权限矩阵

| 权限 | 游客 | 注册读者 | 知友 | 管理员 |
| --- | ---: | ---: | ---: | ---: |
| 查看公开内容 | 是 | 是 | 是 | 是 |
| 查看登录可见内容 | 否 | 是 | 是 | 是 |
| 查看知友可见内容 | 否 | 否 | 是 | 是 |
| 创建文章 | 否 | 否 | 是 | 是 |
| 编辑、删除自己的文章 | 否 | 否 | 是 | 是 |
| 编辑、删除任意文章 | 否 | 否 | 否 | 是 |
| 置顶、推荐文章 | 否 | 否 | 否 | 是 |
| 创建旅行地点 | 否 | 否 | 是 | 是 |
| 编辑、删除自己的旅行地点 | 否 | 否 | 是 | 是 |
| 编辑、删除任意旅行地点 | 否 | 否 | 否 | 是 |
| 上传音乐草稿 | 否 | 否 | 是 | 是 |
| 发布自己的音乐 | 否 | 否 | 是 | 是 |
| 管理、下架任意音乐 | 否 | 否 | 否 | 是 |
| 维护公共歌单 | 否 | 否 | 否 | 是 |
| 管理站点和用户 | 否 | 否 | 否 | 是 |

### 4.4 知友资格作为单一来源

首期不新增 `CONTRIBUTOR` 角色，原因如下：

- 业务要求是“知友可以创作”，知友资格已经由申请和审批流程维护。
- 再增加作者角色会形成“已是知友但没有作者角色”或“不是知友但残留作者角色”的双状态。
- 当前规模不需要完整的角色分配后台。

首期由 `trust_level=FRIEND` 派生创作能力。管理员自动拥有所有创作能力。

如果未来确实需要对单个知友关闭某一项能力，再增加 `user_capability_override` 覆盖表，而不是立即引入复杂 RBAC。覆盖表建议只表达例外：

```text
user_id
capability_code
enabled
reason
updated_by
update_time
```

首期不创建此表，但能力接口应避免把权限判断散落为大量 `trustLevel == 1`，为未来覆盖机制保留统一入口。

## 5. 后端权限架构

### 5.1 能力编码

建议新增稳定的能力编码：

```text
friend-content:view
article:create
travel:create
music:create
```

管理员治理能力仍由 `ROLE_ADMIN` 或管理员专用方法控制，不必全部暴露给普通前端：

```text
article:curate
travel:moderate
music:review
site:manage
user:manage
```

### 5.2 请求时权限装配

当前 `JwtAuthenticationFilter` 每次请求都会根据 token 中的用户 ID 重新加载用户资料，这一点应保留。不要把知友资格永久固化进长时间有效的 JWT。

建议增加 `SecurityAuthorityFactory`：

1. 根据 `roleCode` 生成 `ROLE_ADMIN` 或 `ROLE_USER`。
2. 根据 `trustLevel` 生成知友能力。
3. 管理员自动获得全部能力。
4. 将能力转为 Spring Security authority，例如：

```text
CAP_FRIEND_CONTENT_VIEW
CAP_ARTICLE_CREATE
CAP_TRAVEL_CREATE
CAP_MUSIC_CREATE
```

这样知友被降级、用户被禁用或未来能力被覆盖后，下一次请求即可生效。

### 5.3 `AccessService` 的职责

继续以现有 `AccessService` 作为统一权限入口，但需要明确分层：

#### 身份与能力

```text
isAdmin(user)
isFriend(user)
hasCapability(userId, capabilityCode)
listCapabilities(userId)
```

#### 文章权限

```text
canCreateArticle(userId)
canManageArticle(userId, article)
canCurateArticle(userId)
canViewArticle(userId, article)
canCommentArticle(userId, article)
```

#### 旅行权限

```text
canCreateTravelMemory(userId)
canManageTravelMemory(userId, location)
canViewTravelMemory(userId, location)
```

#### 音乐权限

```text
canCreateMusicSubmission(userId)
canManageMusicTrack(userId, track)
canReviewMusicTrack(userId)
canViewMusicTrack(userId, track)
```

资源所有权判断必须接收具体资源，不能继续使用无资源参数的 `canManageTravelMemory(userId)`。

### 5.4 控制器与服务层边界

- 控制器校验“是否具备进入该操作的基础资格”。
- 服务层校验“是否拥有这一条具体资源”。
- DTO 不接受来自前端的作者 ID、创建者 ID或音乐贡献者 ID。
- 作者字段必须由后端根据当前用户写入。
- 管理员修改其他用户内容时，不自动篡改原作者。
- 所有业务写操作以服务层校验为准，不能只依赖路由守卫或控制器注解。

### 5.5 前端能力返回

`/auth/info`、登录响应中的用户资料建议增加：

```json
{
  "capabilities": [
    "friend-content:view",
    "article:create",
    "travel:create",
    "music:create"
  ]
}
```

前后端必须共享同一套稳定字符串。前端不得自己根据 `trustLevel` 重复推导复杂权限。

保留 `trustLevel` 和 `memberLabel` 用于展示身份；使用 `capabilities` 决定按钮、菜单和路由入口。

## 6. 文章多作者设计

### 6.1 数据模型

文章已经具备 `author_id`，首期无需新增所有权字段。

需要确认并补充以下索引：

```text
(author_id, status, update_time, id)
(status, visibility, publish_time, id)
```

索引最终形式应结合 MySQL 执行计划确定。

### 6.2 创建流程

1. 当前用户必须拥有 `article:create`。
2. 后端将 `author_id` 固定为当前用户 ID。
3. 知友可以保存草稿或直接发布。
4. 非管理员提交的 `is_top`、`is_recommend` 一律忽略并强制为 `0`。
5. 分类只能选择当前有效分类。
6. 标签沿用现有关系模型；首期是否允许临时新建标签由现有标签接口能力决定，不与分类管理权限混在一起。
7. 保存前校验正文和封面文件归当前用户所有。
8. 保存成功后再将相关临时文件转为永久并同步引用。

### 6.3 更新与删除

允许操作的条件：

```text
当前用户是文章作者
或
当前用户是管理员
```

普通作者更新文章时：

- 不可修改作者 ID。
- 不可置顶。
- 不可设置推荐。
- 不可伪造浏览量、点赞量、评论量和发布时间。
- 从草稿首次发布时由后端设置发布时间。
- 已发布文章再次保存时保留原发布时间，除非管理员执行明确的重新发布操作。

删除继续使用逻辑删除。管理员删除他人文章时写入审计日志。

### 6.4 文章可见性

继续使用：

| 值 | 含义 |
| --- | --- |
| `0` | 公开 |
| `1` | 登录可见 |
| `2` | 知友可见 |
| `3` | 私密 |

作者本人和管理员可以查看自己的非公开文章。

公共文章列表必须在数据库查询阶段加入与访问者匹配的可见性条件，避免现有“批量扫描、Java 过滤、再计算可见总数”的方式在文章量和作者量增加后退化。

建议查询逻辑：

- 游客：`status=PUBLISHED AND visibility=PUBLIC`
- 注册读者：已发布且可见性为 `PUBLIC` 或 `LOGIN`
- 知友：已发布且可见性为 `PUBLIC`、`LOGIN` 或 `FRIEND`
- 管理员：公开列表按产品规则返回已发布内容；管理列表单独查看全部状态
- 作者查询自己的工作台：按 `author_id` 查询全部状态，不复用公共列表

### 6.5 策展能力

以下能力仅管理员拥有：

- 置顶。
- 推荐。
- 调整全站分类。
- 全局下架。
- 修改其他作者内容。

知友直接发布不代表可以影响全站首页策展权。首页推荐与默认排序仍由管理员控制。

## 7. 多用户旅行地图设计

### 7.1 聚合所有权

`travel_memory_location` 是旅行内容聚合根。

- `created_by` 表示地点所有者。
- `updated_by` 表示最近一次操作者。
- `travel_memory_stop` 和 `travel_memory_entry` 通过 `location_id` 继承地点所有权。
- 子表不重复增加用户 ID，避免地点与照片出现归属不一致。

历史数据迁移时：

1. 找到站点所有者或管理员用户。
2. 将 `created_by IS NULL` 的地点回填给站点所有者。
3. 将 `updated_by IS NULL` 的地点回填为 `created_by`。
4. 校验无空值后，将 `created_by` 改为非空。
5. 增加创建者查询索引。

不要在新迁移中继续硬编码用户 ID `1`。站点所有者应通过明确配置或站点配置表确定。

### 7.2 写接口

新增面向知友的业务接口：

```text
GET    /travel-memories/mine
POST   /travel-memories
PUT    /travel-memories/{id}
DELETE /travel-memories/{id}
```

保留管理员全局接口：

```text
GET /admin/travel-memories
GET /admin/travel-memories/{id}
```

管理员是否继续使用旧的 `/admin/travel-memories` 写接口可以分阶段兼容，但新服务方法必须统一走资源所有权策略，不能维护两套业务逻辑。

### 7.3 查询接口

公共列表增加可选参数：

```text
creatorId
```

查询顺序必须是：

1. 先根据当前访问者计算允许的可见性。
2. 再按 `creatorId` 筛选。
3. 最后执行排序和分页。

指定 `creatorId` 不能绕过知友可见性。

列表项和详情增加创建者摘要：

```json
{
  "creator": {
    "id": "10001",
    "username": "demo",
    "nickname": "示例用户",
    "avatar": "/..."
  }
}
```

不要在旅行 DTO 中返回邮箱或其他私密用户资料。

### 7.4 可见性

首期建议扩展为：

| 值 | 含义 |
| --- | --- |
| `0` | 公开 |
| `2` | 知友可见 |
| `3` | 私密，仅作者和管理员 |

如果暂时不新增私密值，也应在代码结构上保留扩展位置。旅行草稿或尚未完成的地点更适合使用状态表达，不应仅靠可见性隐藏。

### 7.5 地图前端

旅行地图增加轻量筛选：

- 全部旅途。
- 我的旅途，仅登录知友显示。
- 按知友选择。

地图、地点索引和详情面板使用同一个筛选状态。URL 使用查询参数保存状态：

```text
/memory-map?creatorId=10001
/memory-map?scope=mine
/memory-map?creatorId=10001&focus=20001
```

每个地点展示创建者头像或昵称，但不能让作者标签压过地点、路线和照片本身。

成员主页“旅行”入口直接链接到对应筛选后的地图，不重新建设一套缩小版地图。

## 8. 多用户音乐设计

### 8.1 设计原则

知友是经过站点所有者人工确认的可信用户，因此音乐与文章、旅行地点采用一致的直接发布模型：

- 知友可以创建草稿。
- 知友可以直接发布自己的音乐。
- 作者本人或管理员可以修改和删除。
- 管理员保留全局归档、下架和公共歌单策展权。
- 不增加投稿审核状态、审核列表或审核操作。

直接发布不等于开放公共歌单管理。默认播放集和公共歌单仍属于全站体验，只允许管理员维护。

### 8.2 数据模型

建议在 `music_track` 增加：

```text
contributor_id   bigint   创建者，不为空
```

现有 `status` 足以表达音乐生命周期：

```text
draft
published
archived
```

首期不增加 `review_status`、`review_note`、`reviewed_by`、`reviewed_at` 或 `submitted_at`。

### 8.3 历史音乐归属

历史曲目不能全部直接归给站点所有者。迁移应按以下顺序推断 `contributor_id`：

1. 如果 `music_track.audio_file_id` 对应 `sys_file.user_id`，使用音频文件上传者。
2. 如果音频文件无法推断，但 `cover_file_id` 对应 `sys_file.user_id`，使用封面文件上传者。
3. 如果文件 ID 缺失，可根据受控的音频 URL 或封面 URL查询 `sys_file.user_id`。
4. 只有上述方式都无法推断时，才回退到站点所有者用户 ID `1`。

迁移前应输出以下对账结果：

- 按音频文件推断的数量。
- 按封面文件推断的数量。
- 按 URL 推断的数量。
- 最终回退到用户 `1` 的曲目 ID 列表。

文章继续保留已有 `author_id`。旅行地点继续保留已有 `created_by`，只对空值进行回填。任何迁移都不得覆盖已经存在且有效的历史所有者。

### 8.4 知友操作

知友可以：

- 创建音乐草稿。
- 上传或更换自己的音频与封面。
- 编辑标题、歌手、专辑、歌词、推荐语等元数据。
- 将自己的草稿直接发布。
- 修改自己的已发布音乐。
- 删除自己的草稿或已发布音乐。

限制：

- 不可修改 `contributor_id`。
- 不可修改其他用户音乐。
- 不可把其他用户上传的音频或封面认领为自己的文件。
- 不可维护公共歌单、默认播放集和全局排序权重。
- 删除已发布音乐时必须同步清理歌单关系和文件引用。

如果希望避免已发布音乐因误操作立即消失，可以把普通作者的“删除”实现为归档；管理员仍可执行最终删除。该行为属于实现阶段的交互细节，不影响所有权模型。

### 8.5 管理员操作

管理员可以：

- 查看全部用户音乐。
- 修改、归档或下架任意曲目。
- 将已发布曲目加入公共歌单。
- 调整公共歌单和默认播放集。
- 查看曲目创建者和相关管理员消息。

歌单所有权首期不下放。`music_playlist` 无需增加用户归属字段。

### 8.6 API 设计

知友接口：

```text
GET    /music/tracks/mine
GET    /music/tracks/mine/{id}
POST   /music/tracks
PUT    /music/tracks/{id}
DELETE /music/tracks/{id}
PATCH  /music/tracks/{id}/status
```

`PATCH /music/tracks/{id}/status` 仅允许资源所有者或管理员操作，并限制普通作者只能在 `draft`、`published`、`archived` 三种合法状态间按产品规则切换。

现有管理员曲目和歌单接口可以继续保留，用于全局管理。

现有公共播放接口保持不变，只返回 `status=published` 的曲目。

### 8.7 版权与来源确认

音乐创建页应要求作者确认：

- 自己有权上传并在本网站播放该音频。
- 已填写必要的来源说明。
- 管理员可以因版权、内容或存储原因下架。

该确认不能替代法律审核，但应作为音乐创建记录的一部分。是否增加结构化 `source_type`、`source_url`、`rights_note` 字段，可在音乐模块实施阶段结合真实来源需求确定。

## 9. 文件存储与私有资源设计

### 9.1 当前风险

业务记录设置为知友可见，并不代表图片或音频文件本身是私有的。当前对象存储公共读策略会让已知 URL 绕过业务 API。

在开放多用户创作前，必须把“业务可见性”和“对象访问性”统一起来。

### 9.2 存储分层

推荐使用两个存储桶：

#### 公开桶

用于：

- 公开文章图片和封面。
- 公开头像。
- 公开站点资源。
- 已发布的公共音乐。
- 公开旅行地点图片。

公开桶可以通过 CDN 或固定 URL 访问。

#### 私有桶

用于：

- 知友可见和私密旅行图片。
- 音乐草稿。
- 好友申请附件。
- 其他仅特定用户或管理员可访问的文件。

私有桶禁止匿名读取。

### 9.3 `sys_file` 扩展

建议增加：

```text
storage_scope   varchar   PUBLIC/PROTECTED
bucket_name     varchar   实际存储桶
```

对于受保护文件：

- 数据库保存对象名和桶名。
- 不保存长期有效的预签名 URL。
- DTO 返回受控文件 ID 或站内访问地址。
- 客户端访问时由后端验证业务权限后返回短时效预签名 GET URL，或由后端代理流式输出。

### 9.4 文件认领

将现有“按 URL 转永久”升级为显式文件认领流程：

```text
claimPermanentFiles(
    operatorId,
    fileIds,
    expectedRefType,
    bizRefType,
    bizRefId
)
```

认领前必须校验：

- 文件存在。
- 文件未删除。
- 文件当前为临时状态，或已经属于当前业务。
- `file.user_id` 等于当前用户，管理员迁移或修复操作除外。
- 上传时的 `ref_type` 与业务预期匹配。
- 文件未被其他业务非法占用。

禁止仅凭前端提交的任意 URL 把其他用户文件永久化。

### 9.5 受保护文件迁移

历史迁移建议：

1. 根据 `file_reference` 和业务记录识别知友旅行图片、申请附件和未发布音乐。
2. 将对象复制到私有桶。
3. 更新 `sys_file.bucket_name`、`object_name`、`storage_scope`。
4. 更新业务冗余 URL 或改为通过文件 ID 解析。
5. 验证新访问链路。
6. 删除公开桶中的旧对象，避免旧 URL 持续可用。

迁移必须提供可重复执行、可对账和可回滚的脚本，不能只更新数据库而遗留公开对象。

### 9.6 配额与限制

配额应配置化，不写死在控制器：

- 单图片大小。
- 单音频大小。
- 单用户图片总容量。
- 单用户音频总容量。
- 每日图片上传次数。
- 每日音频上传次数。
- 临时文件过期时间。

可以沿用当前图片 12 MB、音频 60 MB 的单文件限制作为初始默认值，再根据真实存储预算设置用户总容量。

上传校验至少包含：

- 扩展名。
- 浏览器上报 MIME。
- 文件头或实际媒体类型。
- 图片解码或音频基础可读性。
- 文件名清理。

## 10. 公开成员与个人资料

### 10.1 公开成员范围

`/site/members` 不应继续返回全部启用用户。

首期建议只公开：

- 站点所有者。
- 已选择公开资料的知友。

普通注册读者默认不进入成员名录。

### 10.2 用户隐私字段

建议在 `sys_user` 增加：

```text
profile_visibility   tinyint   0-隐藏 1-公开
email_public         tinyint   0-不公开 1-公开
```

迁移默认值：

- 管理员和现有知友：`profile_visibility=1`，但允许用户自行关闭。
- 普通读者：`profile_visibility=0`。
- 所有用户：`email_public=0`。

公开 DTO 只有在 `email_public=1` 时才返回邮箱。个人资料接口仍可向本人返回完整邮箱。

### 10.3 站点所有者

生产环境站点所有者用户 ID 已确认为 `1`。该 ID 只表示站点所有者身份和历史数据无法推断时的最终回退，不表示所有历史内容都应归属于用户 `1`。

建议把该约定收敛为明确配置，消除业务代码中的魔法值：

```text
app.site-owner-user-id
```

配置默认值为 `1`。后端站长资料、成员身份展示和历史迁移的最终回退都从同一来源读取。

历史内容归属遵循“保留或推断优先”：

- 文章保留已有 `author_id`。
- 旅行保留已有 `created_by`，只有空值才回填。
- 音乐优先根据音频或封面对应的 `sys_file.user_id` 推断。
- 仅在无法保留或推断时回退到站点所有者 `1`。

### 10.4 公开成员主页

成员主页建议包含：

- 个人名片。
- 公开文章。
- 当前访问者可见的旅行地点。
- 已发布的音乐贡献。

页面只展示真实贡献，不增加粉丝数、活跃度排行榜等平台化指标。

## 14. 管理员消息中心

### 14.1 目标与边界

知友获得直接发布能力后，管理员不需要逐条审批，但仍需要快速了解站点最近新增了什么。

管理员消息中心用于：

- 提醒站点所有者有新的内容或需要关注的业务事件。
- 在顶部导航头像处显示未读数量。
- 从消息直接定位到对应文章、旅行地点、音乐或好友申请。
- 保留上线后的近期站点动态。

管理员消息不等于审计日志：

- 消息面向管理员日常使用，强调“发生了什么、是否已读、去哪里查看”。
- 审计日志面向追责和问题排查，强调“谁修改了什么、修改前后状态是什么”。
- 一次业务操作可以同时产生一条消息和一条审计事件，但两者不能共用同一张表承担不同职责。

### 14.2 数据表

建议新增 `admin_notification`：

```text
id                    bigint        主键
recipient_user_id     bigint        接收管理员
event_type            varchar(64)   业务事件类型
actor_user_id         bigint        触发事件的用户，可为空
resource_type         varchar(32)   ARTICLE/TRAVEL_MEMORY/MUSIC_TRACK/TRUST_REQUEST
resource_id           bigint        业务资源 ID
title                 varchar(160)  消息标题
summary               varchar(500)  安全的内容摘要
read_status           tinyint       0-未读 1-已读
read_time             datetime      阅读时间
dedupe_key            varchar(160)  幂等键
create_time           datetime      创建时间
update_time           datetime      更新时间
deleted               tinyint       逻辑删除
```

推荐索引：

```text
(recipient_user_id, read_status, create_time, id)
(recipient_user_id, create_time, id)
(resource_type, resource_id, create_time)
UNIQUE (dedupe_key)
```

当前接收管理员为用户 `1`。保留 `recipient_user_id` 而不是设计成全局单一已读状态，未来增加其他管理员时可以为每位管理员生成独立消息和已读状态。

`summary` 只保存标题、作者昵称、状态等安全摘要，不保存文章正文、旅行照片地址、音频 URL、申请附件或其他敏感内容。

### 14.3 首期事件类型

建议首期记录：

```text
ARTICLE_CREATED
ARTICLE_PUBLISHED
TRAVEL_MEMORY_CREATED
MUSIC_TRACK_CREATED
MUSIC_TRACK_PUBLISHED
TRUST_REQUEST_CREATED
```

事件生成规则：

- 新建并直接发布文章：只生成 `ARTICLE_PUBLISHED`，避免同时产生“新建”和“发布”两条重复消息。
- 新建文章草稿：生成 `ARTICLE_CREATED`；以后首次发布时再生成 `ARTICLE_PUBLISHED`。
- 新建旅行地点：生成 `TRAVEL_MEMORY_CREATED`。
- 新建并直接发布音乐：只生成 `MUSIC_TRACK_PUBLISHED`。
- 新建音乐草稿：生成 `MUSIC_TRACK_CREATED`；以后首次发布时再生成 `MUSIC_TRACK_PUBLISHED`。
- 新好友申请：生成 `TRUST_REQUEST_CREATED`，与现有邮件通知并存。

首期不记录：

- 编辑器自动保存。
- 普通内容更新。
- 浏览、点赞、收藏。
- 单个图片、音频或封面的临时上传。
- 后台列表查询。
- 文件清理任务。

如果直接监听 `/upload/music-audio`，用户上传后放弃创建曲目也会产生无效消息，而且音频与封面会形成多条重复消息。因此“音乐上传”在消息语义上定义为成功创建一条 `music_track` 业务记录，而不是底层对象上传完成。

### 14.4 业务事件生成

消息不能在 Controller 中手工拼接，否则后台脚本、服务复用和未来任务入口容易漏记。

建议流程：

1. 文章、旅行、音乐或好友申请服务完成业务写入。
2. 服务发布轻量领域事件，包含事件类型、操作者、资源类型、资源 ID和必要标题快照。
3. 使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 在事务成功提交后生成管理员消息。
4. 通过 `dedupe_key` 保证同一业务事件重复投递时只生成一条消息。
5. 消息写入失败不能回滚已经成功发布的内容，但必须记录稳定错误事件，便于补偿。

建议幂等键：

```text
ADMIN:{recipientUserId}:{eventType}:{resourceType}:{resourceId}
```

首次发布只生成一次。文章或音乐从已发布切回草稿后再次发布，不重复生成“首次发布”消息；如果未来需要记录“重新发布”，应使用单独事件类型。

首期不引入消息队列或 WebSocket。当前站点规模使用 Spring 事务事件和数据库消息表足够。

### 14.5 后端 API

所有接口仅允许管理员：

```text
GET   /admin/notifications
GET   /admin/notifications/unread-count
PUT   /admin/notifications/{id}/read
PUT   /admin/notifications/read-all
DELETE /admin/notifications/{id}
```

列表参数建议：

```text
page
size
readStatus
eventType
```

消息列表 VO 返回：

```json
{
  "id": "10001",
  "eventType": "ARTICLE_PUBLISHED",
  "title": "知友发布了新文章",
  "summary": "小陈发布了《一次夏日旅行记录》",
  "actor": {
    "id": "20001",
    "nickname": "小陈",
    "avatar": "/..."
  },
  "resourceType": "ARTICLE",
  "resourceId": "30001",
  "read": false,
  "createTime": "2026-07-27T15:00:00"
}
```

后端返回资源类型和资源 ID，前端负责映射站内跳转地址，避免消息表长期绑定某个前端路由结构。

删除消息只影响管理员消息列表，不影响对应业务内容。

### 14.6 顶部头像未读数

仅管理员显示未读徽标：

- 管理员登录成功或恢复登录态后立即拉取未读数。
- 页面处于可见状态时每 60 秒低频轮询一次。
- 浏览器重新获得焦点时补拉一次。
- 退出登录、用户不再是管理员或组件卸载时停止轮询。
- 首期不使用 WebSocket 或 SSE。

展示规则：

- `0` 不显示徽标。
- `1-99` 显示真实数量。
- 大于 `99` 显示 `99+`。
- 徽标不能遮挡头像主体和头像菜单点击区域。
- 为读屏提供“有 N 条未读管理员消息”的可访问文本。

头像菜单增加“消息中心”项，并显示同一未读数。点击进入管理后台消息页。

### 14.7 后台消息页

建议新增管理后台页面：

```text
/admin/notifications
```

页面包含：

- 全部、未读筛选。
- 事件类型筛选。
- 按时间倒序的消息列表。
- 单条标记已读。
- 全部标记已读。
- 删除单条消息。
- 点击消息查看对应业务资源。

打开消息列表不自动把全部消息标记为已读。用户点击具体消息时标记该条已读；“全部已读”必须是显式操作。

如果资源已删除或当前不可访问，消息仍可阅读和标记已读，跳转时显示“对应内容已不存在或不可访问”，不能把整条消息列表加载失败。

### 14.8 前端状态管理

建议增加独立 Pinia store：

```text
admin-notification
```

职责：

- 保存未读数。
- 拉取消息分页。
- 标记单条已读。
- 全部已读。
- 控制轮询生命周期。
- 在消息状态变化后同步头像徽标。

普通用户不调用管理员消息 API。后端仍需返回 403，不能只依赖前端隐藏。

## 15. 审计与治理

### 15.1 审计事件

建议为高风险操作记录结构化事件：

```text
ARTICLE_ADMIN_UPDATE
ARTICLE_ADMIN_DELETE
TRAVEL_ADMIN_UPDATE
TRAVEL_ADMIN_DELETE
MUSIC_CREATE
MUSIC_PUBLISH
MUSIC_ARCHIVE
USER_TRUST_GRANTED
USER_TRUST_REVOKED
```

首期可以先使用稳定日志事件码；如果需要后台检索，再增加 `operation_audit_log` 表。

### 15.2 管理员覆盖操作

管理员修改或删除他人内容时至少记录：

- 操作者。
- 资源类型。
- 资源 ID。
- 原所有者。
- 操作类型。
- 时间。
- 可选原因。

### 15.3 知友降级

知友被降级为读者后：

- 下一次请求立即失去知友内容访问能力。
- 立即失去新增和修改内容的能力。
- 已发布公开内容保持可见。
- 草稿和私密内容保留，不自动转移所有权。
- 管理员可以归档、保留或转移内容。
- 已发布公开音乐保持可见，管理员可以归档或转移；原作者立即失去后续编辑能力。

### 15.4 用户禁用

用户被禁用后：

- JWT 在下一次请求加载用户时失效。
- 不能继续上传或创作。
- 已公开内容不自动删除。
- 管理员决定是否下架。

## 16. 性能与查询

多作者后需要重点关注：

### 16.1 文章列表

公共文章可见性过滤必须下推 SQL，不能扫描全部已发布文章后在 Java 中过滤。

### 16.2 成员主页

文章、旅行和音乐列表均需分页。贡献数量可以通过独立聚合接口返回，避免为了统计总数拉取大量记录。

### 16.3 旅行地图

如果地点规模仍较小，可以一次返回当前筛选范围内的所有标记；当数量增长后再增加：

- 地图边界框查询。
- 地图级别聚合。
- 分页地点索引。

首期不提前实现地理空间索引，但普通索引必须覆盖创建者、状态和可见性。

### 16.4 文件配额

用户容量统计优先基于 `sys_file.user_id + status + file_size` 聚合，并为常用条件建立索引。规模扩大后可增加异步配额快照，首期无需提前维护冗余统计表。

## 17. 安全要求

### 17.1 防止越权

必须覆盖以下 IDOR 场景：

- 知友修改另一位知友文章。
- 知友删除另一位知友旅行地点。
- 知友读取另一位知友私密地点。
- 知友修改另一位知友音乐草稿。
- 用户认领另一位用户上传的临时文件。
- 读者直接调用知友写接口。
- 被降级知友使用旧页面或旧 token 继续写入。

### 17.2 输入与内容安全

- Markdown 和富文本渲染继续执行安全清理，禁止存储型 XSS。
- 文件名、歌词来源、链接和外部 URL 做长度和协议校验。
- 旅行经纬度和日期范围继续由后端校验。
- 音乐状态使用枚举，不接受任意字符串。
- 所有作者 ID、创建者 ID和消息接收人 ID由后端写入。

### 17.3 限流

至少对以下接口增加按用户限流：

- 图片上传。
- 音频上传。
- 文章创建。
- 旅行地点创建。
- 音乐创建和发布。

知友已经由站点所有者人工确认，但限流仍用于防止账号泄露、误操作和异常客户端重试。

## 18. 实施阶段

### 阶段 0：权限和隐私基础

目标：先建立后续模块共用的安全边界。

工作项：

- 能力编码与权限装配。
- `/auth/info` 返回能力集合。
- `AccessService` 资源所有权接口。
- 公开用户邮箱默认隐藏。
- 成员名录只展示允许公开的成员。
- 站点所有者配置化。
- 文件所有权认领校验。
- 管理员消息表、事件模型和幂等键。
- 权限矩阵测试。

完成后仍可保持所有写入口管理员专用，不急于开放。

### 阶段 1：多作者文章

目标：用成本最低的文章模块验证整套能力和所有权模型。

工作项：

- 知友创建文章。
- 作者或管理员编辑、删除。
- 管理员独占置顶和推荐。
- 前端文章编辑路由能力化。
- 创作中心“我的文章”。
- 公共文章 SQL 可见性过滤优化。
- 文章文件归属校验。
- 管理员消息 API、后台消息页和头像未读徽标。
- 文章创建与首次发布消息。

### 阶段 2：多用户旅行地图与私有图片

目标：实现按知友展示地点，并确保知友照片真正受保护。

工作项：

- 旅行地点所有权迁移。
- 知友 CRUD。
- `creatorId` 和 `mine` 查询。
- 创建者 DTO。
- 地图筛选和成员主页旅行入口。
- 私有桶、鉴权下载或预签名访问。
- 历史知友图片迁移。
- 旅行地点创建消息。

### 阶段 3：多用户音乐

目标：知友可以创建和直接发布自己的音乐，管理员继续策展公共歌单并保留全局治理权。

工作项：

- 音乐创建者字段。
- 历史曲目按文件上传者推断归属。
- 音乐草稿、发布和所有者接口。
- 音频上传能力与配额。
- 已发布音乐转公开存储。
- 创作中心“我的音乐”。
- 音乐创建与首次发布消息。

### 阶段 4：成员贡献与治理完善

目标：让多用户内容在公开侧形成完整体验。

工作项：

- 成员主页文章、旅行、音乐页签。
- 贡献汇总。
- 管理员跨用户内容检索。
- 消息中心筛选和治理体验完善。
- 审计日志后台。
- 配额查看和文件治理。
- 根据真实使用情况决定是否增加单用户能力覆盖。

## 19. 功能开关与发布策略

建议增加模块级功能开关：

```text
multi-user.article-creation-enabled
multi-user.travel-creation-enabled
multi-user.music-creation-enabled
admin-notification.enabled
```

发布顺序：

1. 先部署数据库和兼容后端，开关默认关闭。
2. 部署支持能力判断的前端。
3. 使用管理员和测试知友验证。
4. 按模块逐个开启。

回滚时：

- 关闭功能开关即可停止新建入口。
- 已有内容和旧公开 API 保持可读。
- 不删除迁移字段。
- 不把历史数据回滚为无所有者状态。

## 20. 测试方案

### 20.1 后端单元与服务测试

每个资源至少覆盖：

- 管理员。
- 内容所有者知友。
- 非所有者知友。
- 注册读者。
- 游客。
- 被禁用用户。
- 已降级知友。

### 20.2 控制器测试

验证：

- 未登录返回 401。
- 无能力返回 403。
- 资源不存在返回 404。
- 非所有者操作返回 403。
- 管理员覆盖操作成功。
- DTO 无法伪造所有者。

### 20.3 可见性测试

文章和旅行分别验证：

- 公开。
- 登录可见。
- 知友可见。
- 私密。
- 作者本人。
- 管理员。

列表、详情、上一篇/下一篇、热门、推荐和成员主页不能出现可见性不一致。

### 20.4 文件测试

验证：

- 用户不能认领其他用户文件。
- 受保护文件匿名访问失败。
- 合法知友可以获得短时访问地址。
- 短时地址过期后不可用。
- 草稿音乐不会进入公开桶。
- 音乐发布后公共播放正常。
- 临时文件过期清理不删除已认领文件。

### 20.5 管理员消息测试

验证：

- 功能上线前的历史内容不产生消息。
- 新建草稿、直接发布和首次发布按规则生成正确消息。
- 同一事件重复投递不会生成重复消息。
- 业务事务回滚时不生成消息。
- 消息写入失败不回滚已成功内容，并留下错误日志。
- 普通用户无法调用消息 API。
- 单条已读、全部已读和未读数量一致。
- 删除业务资源后消息列表仍可正常加载。

### 20.6 前端验证

至少验证：

- 不同身份看到的菜单和按钮正确。
- 直接输入受限路由时有明确反馈。
- 后端返回 403 时页面不会误报为“内容不存在”。
- 创作中心桌面和移动端均可用。
- 地图筛选、URL 状态和返回 focus 正常。
- 音乐草稿、发布和归档状态清晰。
- 管理员头像未读数、`99+`、轮询停止和消息跳转正确。
- 长中文昵称、标题和消息摘要不会破坏布局。

前端改动完成后执行：

```text
npm run check:element-boundary
npm run build
```

后端执行针对性测试，并在完整阶段执行 Maven 测试。

## 21. 验收标准

### 权限

- 读者无法通过前端或直接 API 创建内容。
- 知友可以创建并管理自己的文章和旅行地点。
- 知友无法管理其他用户内容。
- 管理员可以治理所有内容。
- 知友降级后权限在下一次请求立即失效。

### 文章

- 知友可以保存草稿和发布文章。
- 非管理员无法置顶或推荐。
- 作者主页正确展示其公开文章。
- 各可见性在列表和详情中一致。

### 旅行

- 地图可以按创建者筛选。
- 指定用户筛选不会泄露不可见地点。
- 知友只能修改自己的地点。
- 知友和私密旅行图片不能通过永久公共 URL 绕过鉴权。

### 音乐

- 知友可以创建草稿并直接发布自己的音乐。
- 知友不能修改其他用户音乐。
- 只有管理员可以维护公共歌单和下架任意音乐。
- 发布后的音频可以稳定播放。

### 管理员消息

- 新文章、新旅行地点和新音乐按规则生成管理员消息。
- 历史数据不补消息。
- 管理员头像显示准确未读数。
- 普通用户看不到徽标且无法访问消息接口。
- 点击消息能够定位业务资源，资源不存在时有稳定降级。
- 标记已读后头像和后台列表状态同步。

### 隐私与文件

- 公开成员接口默认不返回邮箱。
- 普通读者默认不进入公开成员名录。
- 用户不能占用或永久化他人上传文件。
- 配额和限流可以配置并生效。

## 23. 推荐默认决策

为减少第一版的未决项，建议采用以下默认策略：

1. 所有知友默认获得文章、旅行和音乐创建能力。
2. 知友文章可以直接发布。
3. 知友旅行地点可以直接发布。
4. 知友音乐可以直接发布，不增加管理员审核流程。
5. 公共歌单始终由管理员维护。
6. 普通读者不进入公开成员名录。
7. 邮箱默认不公开。
8. 管理员保留全局编辑、归档和删除权。
9. 知友降级不自动删除其已公开内容。
10. 私密与知友文件使用私有存储，不接受仅靠隐藏 URL 的方案。
11. 历史内容保留已有所有者，音乐按关联文件上传者推断，无法推断才回退到用户 `1`。
12. 管理员消息只记录功能上线后的业务事件，不补历史消息。
13. 管理员头像采用登录后拉取、浏览器聚焦补拉和 60 秒低频轮询，不引入 WebSocket。

## 24. 后续决策点

进入各阶段实施前仍需确认：

1. 知友是否允许把旅行地点设置为完全私密。
2. 知友资料是否在审批通过后默认公开，还是由用户手动开启。
3. 单用户图片和音频容量的默认值。
4. 私有文件采用后端代理下载还是短时效预签名 URL。
5. 管理员修改他人内容时是否要求填写原因。
6. 是否在第一版就建设数据库审计表，还是先使用结构化日志。
7. 管理员消息保留期限，以及是否需要自动清理已读旧消息。

这些决策不影响总体架构，可以在对应阶段开始前确定。
