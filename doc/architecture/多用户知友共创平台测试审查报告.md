## 6. 发布阻断缺陷

### BUG-001：降级用户仍可修改和删除历史内容

| 属性 | 内容 |
| --- | --- |
| 严重程度 | P0 |
| 类型 | 授权绕过、撤权失效 |
| 影响范围 | 文章、旅途、音乐 |
| 是否阻断发布 | 是 |

#### 设计预期

知友被降级为普通读者或用户被禁用后，应立即失去三类内容的创建、修改和删除能力；已经公开发布的内容可以继续展示，但不能继续由已撤权用户维护。

#### 当前实现

三个资源管理方法仅判断“管理员或资源所有者”，没有再次检查当前用户是否仍具有对应创建能力：

- [`AccessServiceImpl.canManageTravelMemory`](../../src/main/java/com/chen404/service/impl/AccessServiceImpl.java)
- [`AccessServiceImpl.canManageArticle`](../../src/main/java/com/chen404/service/impl/AccessServiceImpl.java)
- [`AccessServiceImpl.canManageMusicTrack`](../../src/main/java/com/chen404/service/impl/AccessServiceImpl.java)

文章、旅途、音乐更新和删除接口继续直接使用这些管理判断。因此，已被降级的原作者仍可通过 API 修改或删除历史资源。

#### 建议修复

非管理员管理资源时应同时满足：

1. 当前用户状态有效。
2. 当前用户仍具有对应资源的创作能力。
3. 当前用户是资源所有者。

管理员可作为独立分支保留管理能力。

#### 必补测试

- 知友创建文章后被降级，更新和删除返回 403。
- 知友创建旅途后被降级，更新和删除返回 403。
- 知友创建音乐后被降级，更新、状态切换和删除返回 403。
- 用户被禁用后，三类资源写接口均不可访问。
- 已公开内容在用户降级后仍可正常公开读取。

### BUG-002：文件永久化存在跨用户认领风险

| 属性 | 内容 |
| --- | --- |
| 严重程度 | P0 |
| 类型 | IDOR、文件归属绕过 |
| 影响范围 | 文章、旅途、音乐、信任申请附件 |
| 是否阻断发布 | 是 |

#### 当前实现

`SysFileService.convertToPermanent` 只接收文件 URL、引用类型和业务 ID。实现会按 URL 查询文件，然后直接修改永久状态及业务引用，没有校验：

- 当前操作者；
- 文件原上传者；
- 文件是否仍为临时状态；
- 文件是否已被其他业务占用；
- 文件类型是否与目标业务一致；
- 文件 ID 和 URL 是否指向同一条记录。

文章和旅途会直接使用解析出的 URL 进行永久化。攻击者只要知道其他用户临时文件的 URL，就可能将其挂接到自己的资源。

音乐虽然增加了文件归属校验，但当请求同时包含 `fileId` 和 `fileUrl` 时，校验优先使用 `fileId`，永久化却使用 `fileUrl`。攻击者可以提交“自己的文件 ID + 他人的文件 URL”绕过校验。

#### 建议修复

按设计方案新增显式认领接口，例如：

```java
claimPermanentFiles(
    Long operatorId,
    List<Long> fileIds,
    String expectedRefType,
    String bizType,
    Long bizId
)
```

认领操作必须在同一事务内校验：

1. `file.user_id == operatorId`，管理员代管场景另行显式授权。
2. 文件状态为临时状态。
3. 文件未删除、未过期。
4. 文件引用类型与业务类型一致。
5. 文件 ID、URL、对象名属于同一条记录。
6. 文件未被不兼容的其他业务占用。
7. 重复提交时保持幂等。

业务接口应只提交文件 ID，不再依靠正文 URL 作为文件所有权凭证。

### BUG-003：受保护内容缺少真正的私有文件访问

| 属性 | 内容 |
| --- | --- |
| 严重程度 | P0 |
| 类型 | 隐私泄露 |
| 影响范围 | 知友可见旅途、草稿内容、未发布音乐及附件 |
| 是否阻断发布 | 是 |

设计中的 `storage_scope`、`bucket_name`、公共桶/保护桶拆分、签名 URL 或后端鉴权代理尚未落地。数据库迁移和 `SysFile` 实体中也未形成完整的存储范围模型。

如果当前 MinIO 对象 URL 可以直接访问，则业务接口上的“知友可见”只能保护元数据接口，不能保护文件本身。

建议先完成：

1. 公共和保护对象的存储范围字段。
2. 受保护文件上传到私有桶。
3. 下载时按业务可见性鉴权。
4. 返回短期签名 URL，或通过后端受控下载。
5. 已有对象的可重复执行迁移和回滚方案。

## 7. P1 重要缺陷

### BUG-004：公开成员列表暴露全部启用用户

当前 `UserServiceImpl.listPublicUsers()` 查询所有启用用户，`getPublicUser()` 也允许读取任意启用用户的公开资料。

这与设计中的“站主 + 主动公开资料的知友”不一致，普通读者也可能出现在公开成员列表中。虽然当前 DTO 不写入邮箱，但成员身份、昵称、头像、简介和加入时间仍会被公开。

建议落地：

- `profile_visibility`；
- `email_public`；
- 普通读者默认隐藏；
- 知友可自行关闭公开主页；
- 站主配置是否展示公开邮箱；
- 公开列表与公开详情使用相同的可见性谓词。

### BUG-005：Snowflake 用户 ID 在前端发生精度丢失

后端用户主键使用 `IdType.ASSIGN_ID`。公开成员 DTO 已通过字符串序列化保护长整型，但前端调用公开成员详情和地图创建者筛选时又执行 `Number(id)`。

典型受影响位置：

- `Chen404Fro/src/api/home.ts`
- `Chen404Fro/src/views/MemoryMap/MemoryMap.vue`

当用户 ID 大于 `Number.MAX_SAFE_INTEGER` 时，可能出现：

- 成员主页请求错误用户或返回 404；
- “在地图查看全部”无法匹配正确创建者；
- 缓存键、路由参数和比较逻辑不一致。

建议所有用户 ID、文章 ID等 Snowflake ID 在 TypeScript、路由、SDK 和 JSON 中全链路使用字符串。

### BUG-006：无权创建文章被错误转换为 HTTP 400

文章服务会对无创作能力用户抛出 `ForbiddenException`，但 `ArticleController.createArticle()` 捕获所有 `RuntimeException` 并统一返回 `BAD_REQUEST`。

这会导致：

- 权限失败返回 400 而不是 403；
- 前端无法区分参数错误和权限撤销；
- 安全审计和接口契约不准确。

建议移除该通用捕获，或先透传 `UnauthorizedException`、`ForbiddenException`，由全局异常处理器统一生成 401/403。

### TEST-001：关键安全场景没有自动化覆盖

首次审查时后端 131 项测试虽然全部通过，但测试代码中未找到以下关键场景：

- 用户降级或禁用后的撤权；
- 管理员通知写入、事务回滚、去重和失败隔离；
- 跨用户文件认领；
- 文件 ID 与 URL 不一致；
- 公开资料可见性；
- 私有文件直接 URL 访问；
- 三类资源的跨所有者 IDOR。

首次审查时的旅途权限测试只验证管理员、所有者、其他用户，没有验证“原所有者已被降级”，所以当时的测试全绿不能作为多用户安全上线依据。本轮已补充统一撤权、文件认领、保护文件访问、资料隐私和通知监听器等核心单元测试，测试总数增至 141 项；生产对象迁移和真实环境端到端复测仍是独立的发布准入条件。

## 8. P2 功能与质量问题

### 8.1 文章公开列表在 Java 中扫描过滤

`ArticleServiceImpl.buildVisibleArticlePage()` 会分批读取文章，在 Java 中过滤可见性并重新累计总数。数据量增长后会导致：

- 查询次数随文章数量增长；
- 深分页变慢；
- 列表总数计算成本高；
- 可见性规则更难使用数据库索引。

建议将状态、可见性、作者和访问者身份条件统一下推 SQL，并增加组合索引和执行计划测试。

### 8.2 文章再次发布会重置首次发布时间

文章从草稿变为发布时会直接设置当前时间。已发布文章转回草稿后再次发布，也会覆盖原 `publishTime`，与设计中的“首次发布时间不重置”不一致。

建议只在历史 `publishTime` 为空时写入首次发布时间；如果需要记录重新发布，使用独立事件和字段。

### 8.3 创作中心尚未达到设计目标

当前创作中心已经提供三类创作入口和基础列表，但仍缺少：

- 文章、旅途、音乐 Tab；
- 分页或游标加载；
- 状态筛选；
- 关键词搜索；
- 预览；
- 删除及二次确认；
- 失败重试和局部错误状态；
- 降级后的明确只读提示。

当前文章一次加载 100 条，不适合作为长期列表方案。回收站文章的徽标分支也会显示为“草稿”，与状态标签不一致。

### 8.4 存在嵌套交互元素

创作中心和 Header 中存在 `<router-link><UiButton /></router-link>` 结构，最终可能渲染为 `<a><button></button></a>`。这是无效的嵌套交互元素，可能影响键盘焦点、点击区域和辅助技术。

建议让 `UiButton` 支持 `as`/`to`，或直接把路由链接样式化为按钮。

### 8.5 管理员通知交互不完整

当前通知页和角标已可使用，但仍有以下差距：

- 前端没有事件类型筛选；
- 浏览器页面隐藏时仍持续轮询；
- 资源已删除或不可访问时缺少稳定的降级提示；
- 缺少专用前后端自动化测试；
- `admin-notification.enabled` 功能开关未落地。

### 8.6 前端包体偏大

生产构建成功，但 `AdminLayout` 相关产物约 1.22 MB。后台多个子页面被同步打入同一路由块。

建议对后台子页面使用 `defineAsyncComponent` 或动态导入，并检查文章编辑器、地图和管理端依赖能否按页面拆包。

## 9. 设计层面评价

### 9.1 设计优点

设计方案整体结构清晰，以下原则值得保留：

1. 将能力、资源所有权、状态和可见性作为四个正交维度。
2. 避免为了少量创作者引入过重的通用 RBAC。
3. 明确作者字段不能由请求体直接信任。
4. 将文件安全放在多用户开放前置阶段。
5. 通知采用提交后事件，避免通知失败回滚业务。
6. 明确降级用户、IDOR、文件认领和通知事务测试矩阵。
7. 使用功能开关控制逐类开放和快速回滚。

### 9.2 设计与实现的偏差

首次审查时的最大问题不是设计缺失，而是实施顺序偏离设计：

- 设计要求先完成文件和隐私基线，再开放知友写入；
- 当时文章、旅途、音乐写入入口已经实现，但文件保护、资料可见性和功能开关尚未完成。

本轮已补齐新上传文件保护、资料可见性、能力撤权和功能开关，并让生产配置默认关闭多用户写入与通知。历史对象迁移仍需按运行手册完成，因此当前可以进入受控联调，但还不能跳过发布准入直接对生产用户开放。

按本轮实现结果更新验收状态如下：

| 验收项 | 计划阶段 | 实现状态 | 代码位置 | 测试用例 | 发布阻断 |
| --- | --- | --- | --- | --- | --- |
| 降级立即撤权 | 阶段 0 | 已完成 | AccessService | AUTH-004～006 | 是 |
| 显式文件认领 | 阶段 0 | 已完成 | SysFileService | FILE-001～006 | 是 |

## 11. 修复优先级建议

### 第一阶段：发布阻断

1. 修复降级和禁用用户的存量资源写权限。
2. 将文件永久化改为显式文件 ID 认领，并验证操作者、归属和类型。
3. 建立保护桶、存储范围和鉴权访问。
4. 为上述场景补充自动化测试。

### 第二阶段：隐私与接口一致性

1. 增加公开资料和邮箱公开开关。
2. 将 Snowflake ID 全链路改为字符串。
3. 修正文章创建接口的 401/403/400 语义。
4. 补充跨用户 IDOR 和公开资料测试。

### 第三阶段：功能完整性

1. 完善创作中心分页、筛选、搜索、预览和删除。
2. 完善管理员通知筛选、隐藏页轮询和异常状态。
3. 修复首次发布时间和回收站徽标。
4. 增加音乐版权或来源确认。

### 第四阶段：性能与发布治理

1. 将文章可见性过滤下推 SQL。
2. 优化后台路由拆包。
3. 落地 `multi-user.*` 和 `admin-notification.enabled`。
4. 增加上传配额、频率限制和业务审计日志。
5. 执行真实环境端到端测试、迁移演练和回滚演练。

## 12. 发布准入标准

只有同时满足以下条件，才建议开放知友写入权限：

- [x] 降级和禁用用户不能修改、删除历史内容。
- [x] 三类资源均不能认领其他用户文件。
- [x] 文件 ID 和 URL 不一致时请求会被拒绝。
- [x] 新上传的知友可见或私有文件不使用公开直链。
- [x] 普通读者默认不出现在公开成员列表。
- [x] 本次涉及的 Snowflake 用户 ID 链路保持字符串精度。
- [x] 权限失败稳定返回 401/403，而不是 400。
- [x] 已补充三类资源统一撤权和文件跨所有者测试。
- [x] 管理员通知已补提交后写入、去重/失败隔离核心测试。
- [x] 后端测试、前端边界检查和生产构建全部通过。
- [x] 功能开关可以分别关闭文章、旅途、音乐和通知能力。
- [ ] 已完成生产数据库与对象存储迁移、备份和回滚演练。
- [ ] 已在真实登录态、Redis、数据库和 MinIO 环境完成端到端复测。

## 13. 最终结论

多用户共创的业务主干已经建立，文章、旅途、音乐和管理员通知均有实际实现，方向与设计方案总体一致。

首次审查指出的代码级安全边界已经修复：资源所有权重新绑定当前能力，文件永久化不再单独信任 URL，新上传的受保护文件也已进入私有桶和短时票据链路。

建议生产环境继续保持多用户写入开关关闭，先执行历史对象迁移运行手册，再完成真实登录态、数据库、Redis、MinIO 和匿名对象直链的端到端复测。通过后可按文章、旅行、音乐的顺序逐项开启，而不需要一次性全量开放。
