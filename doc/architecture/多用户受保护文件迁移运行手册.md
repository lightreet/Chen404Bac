# 多用户受保护文件迁移运行手册

## 1. 目的

从本次多用户改造开始，新上传的文章正文图片、文章封面、旅行图片、音乐音频、音乐封面和知友申请附件会直接写入私有存储桶，并通过 `/api/files/{id}` 与短时票据访问。

Flyway 迁移 `V2026072702__harden_multi_user_security.sql` 只增加存储范围字段。历史对象仍保留 `PUBLIC`，不得在数据库迁移事务中直接搬运 MinIO 对象。本手册用于上线时完成历史对象清点、复制、引用替换、验证和延迟清理。

## 2. 适用范围

需要迁移到保护桶的 `sys_file.ref_type`：

- `ARTICLE_CONTENT`
- `ARTICLE_COVER`
- `TRAVEL_MEMORY_IMAGE`
- `MUSIC_AUDIO`
- `MUSIC_COVER`
- `TRUST_REQUEST_ATTACHMENT`

头像、站点 Logo、Hero 图片等明确公开资源继续保留在公共桶。

## 3. 上线前提

1. 备份数据库和公共 MinIO 桶。
2. 部署包含 `storage_scope`、`bucket_name`、保护桶和 `/api/files/{id}` 的兼容后端。
3. 配置 `MINIO_PROTECTED_BUCKET_NAME`，确认该桶无匿名读取策略。
4. 保持以下生产开关关闭：

```text
MULTI_USER_ARTICLE_CREATION_ENABLED=false
MULTI_USER_TRAVEL_CREATION_ENABLED=false
MULTI_USER_MUSIC_CREATION_ENABLED=false
ADMIN_NOTIFICATION_ENABLED=false
```

5. 在维护窗口暂停相关上传和内容编辑，避免清单生成后出现新的历史对象。

## 4. 生成不可变迁移清单

先查询候选记录并保存为带时间戳的 CSV/JSONL，不直接更新：

```sql
SELECT
  id,
  object_name,
  file_url,
  ref_type,
  ref_id,
  user_id,
  status,
  storage_scope,
  bucket_name
FROM sys_file
WHERE deleted = 0
  AND status = 'PERMANENT'
  AND storage_scope = 'PUBLIC'
  AND ref_type IN (
    'ARTICLE_CONTENT',
    'ARTICLE_COVER',
    'TRAVEL_MEMORY_IMAGE',
    'MUSIC_AUDIO',
    'MUSIC_COVER',
    'TRUST_REQUEST_ATTACHMENT'
  )
ORDER BY id;
```

清单必须包含 `old_file_url`、目标稳定 URL `/api/files/{id}`、源桶、目标桶、复制结果、校验结果和后续删除结果。清单是回滚依据，不得覆盖。

## 5. 复制对象

使用 MinIO Client 或等价 S3 工具按清单逐条复制，目标对象名保持 `object_name` 不变。示例中的别名和桶名需要替换为实际值：

```text
mc cp source/chen404/{object_name} target/chen404-protected/{object_name}
mc stat target/chen404-protected/{object_name}
```

要求：

- 复制阶段不删除公共桶对象。
- 每条记录校验目标对象存在、大小一致；可行时同时校验 ETag 或内容哈希。
- 任一复制失败时停止数据库切换，修复后从清单中的失败项重跑。
- 保护桶不得配置匿名 `s3:GetObject`。

## 6. 切换数据库与业务引用

对象全部复制成功后，由一次性迁移程序按清单执行以下操作，并将每条更新结果写入运行日志：

1. 将业务表中的旧 URL 替换为 `/api/files/{id}`：
   - `article.content`
   - `article.cover_image`
   - `travel_memory_entry.image_url`
   - `music_track.audio_url`
   - `music_track.cover_url`
   - `file_reference.file_url` 等现有引用字段
2. 将对应 `sys_file.file_url` 更新为 `/api/files/{id}`。
3. 将 `sys_file.storage_scope` 更新为 `PROTECTED`。
4. 将 `sys_file.bucket_name` 更新为实际保护桶名。
5. 保留 `object_name`、`user_id`、`ref_type`、`ref_id` 和文件状态不变。

文章正文可能包含多个文件 URL，不能使用一次无序 `UPDATE ... JOIN` 代替逐条替换。迁移程序必须按文件 ID 稳定排序，并校验每个旧 URL 的替换次数；实际替换次数与清单预期不一致时应回滚该批次并人工核查。

## 7. 验证

数据库切换后、公共对象删除前完成以下验证：

1. 管理员、内容所有者、知友、普通读者和匿名用户分别验证文章、旅行、音乐和申请附件。
2. 草稿、私密文章、知友可见旅行和未发布音乐的元数据及文件访问权限一致。
3. 匿名请求保护桶对象 URL 不得成功。
4. `/api/files/{id}` 无票据访问保护资源不得成功。
5. 业务详情返回的短时票据可访问，过期后不可继续使用。
6. 随机抽样核对文件内容、大小和页面渲染。
7. 运行文件引用重建任务并确认没有悬空引用。

## 8. 延迟删除与回滚

建议保留公共桶原对象至少一个观察周期。观察期内：

- 发现问题时，使用清单把业务 URL、`sys_file.file_url`、`storage_scope` 和 `bucket_name` 恢复为旧值。
- 保护桶复制件可以保留，不影响旧链路回滚。
- 不要回滚 `V2026072702` 的字段结构。

观察期结束且验证通过后，才按清单逐条删除公共桶原对象。删除后再次验证匿名直链不可访问，并保存删除结果。

## 9. 开启顺序

1. 先开启 `ADMIN_NOTIFICATION_ENABLED`，验证管理员消息。
2. 分别开启文章、旅行、音乐创作开关。
3. 每开启一个模块，都完成一次创建、发布、撤权、跨用户文件认领和保护文件访问冒烟测试。
4. 任一模块异常时只关闭对应开关，不删除已迁移字段或内容归属。
